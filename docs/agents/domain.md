# Domain Docs

工程技能在探索代码库时，应当如何消费本仓库的领域文档。

## 探索之前先读

- 仓库根目录的 **`CONTEXT.md`** —— 术语表
- **`docs/adr/`** —— 读与你要动的区域相关的 ADR
- **`docs/api-contract.md`** —— HTTP / WS 契约。**动接口之前必读**：它是前后端两个
  agent 之间的接缝，单方面改实现而不改它（或不通知对方）就是悄悄毁约。

本仓库是**单上下文**，没有 `CONTEXT-MAP.md`。master / agent / console 三块职责不同，
但共享同一套术语（基线、草稿、下发、接入、回源 mTLS、校验端点），拆成多上下文只会让
同一个词在三处各写一遍然后慢慢漂开。

这些文件缺失时**静默继续**：不要提示它们不存在，也不要建议预先创建。
`/domain-modeling` 技能会在术语或决定真正被确定下来时惰性创建它们。

## 文件结构

```
/
├── CLAUDE.md                  ← 权威优先级：ADR > api-contract > CONTEXT
├── CONTEXT.md                 ← 术语表
├── docs/
│   ├── adr/                   ← 架构决定（0001–）
│   ├── api-contract.md        ← HTTP / WS 契约，前后端接缝
│   └── agents/                ← 本目录：技能的配置
├── cmd/            master 与 agent 两个可执行体（见 issue #17）
├── internal/       主控与 Agent 的实现
├── proto/          gRPC 隧道
│   （迁移在 internal/store/migrations/，因为 Go 的 embed 够不到父目录）
└── web/            Vue 3 控制台（由 frontend agent 维护，后端不动）
```

这几个目录曾经有一句「尚未创建」的说明——那是 #17 之前的事实，现在它们都在。
一份描述现状的文档过期之后不会报错，只会安静地误导下一个读它的人。

## 两个 agent 并行

同一仓库、目录级隔离：后端拿 `cmd/` `internal/` `proto/` `migrations/` `docs/` 与根级
`go.mod`，前端（agent 名 `frontend`）拿 `web/`。`CONTEXT.md`、`docs/adr/`、
`docs/api-contract.md` 两边共享——改这三样要通知对方，别指望它会主动读 diff。

ADR 编号也共享：开新 ADR 前先 `ls docs/adr/`，撞号时**后写的那个改**。

## 使用术语表里的措辞

输出里提到领域概念时（issue 标题、重构提案、假设、测试名），用 `CONTEXT.md` 里定义的
那个词，不要漂到术语表明确列在 `_Avoid_` 里的同义词。

这不只是文风问题：`audit_logs.action` 与事件流 `msg` 由后端产生、在前端页面上原样显示，
所以措辞是**契约的一部分**（取值表见 `docs/api-contract.md` §5）。

尤其注意几个已经被明确区分开的：

- **下发** 是把选中的草稿合入基线并广播的完整过程。全站统一用它，
  **不要**说推送 / 发布 / 部署——设计稿里三个词混用过，已经统一掉了。
- **回源 mTLS** 指边缘节点向源站出示客户端证书，**不是**「要求访问者出示证书」。
  单说「mTLS」或「双向认证」在这个项目里方向是歧义的（ADR-0008）。
- **可读表示** 指工作台右栏那份 JSON，它**不是**将要下发的字节。别叫它「预览 JSON」
  或「Caddy JSON 预览」——那两种叫法会让人以为它可下发（ADR-0007）。
- **配置漂移** 只比对版本号，回答「这次下发到没到」，**不检查节点上的配置内容**（ADR-0002）。
- **证书清单** 是 Agent 上报的**回执**，不是账本——主控自己持有全部签发记录（ADR-0010）。

如果你需要的概念还不在术语表里，那是个信号：要么你在发明这个项目不用的语言（重新考虑），
要么确实存在缺口（记下来交给 `/domain-modeling`）。

## 与 ADR 冲突时要挑明

如果你的输出与某条既有 ADR 相抵触，显式说出来，不要静默覆盖：

> _与 ADR-0004（主控不跑 caddy validate）相抵触——但值得重开，因为……_

**设计项目（claude.ai/design）里的三份文档冻结在 v1.0，已知有 9 处与 ADR 相抵触。**
与 ADR 冲突时**以 ADR 为准**，清单见 `CLAUDE.md` 的「权威在哪」与
`docs/api-contract.md` 末尾的差异对账表。


## 带保质期的句子

「目前尚未」「暂时」「本切片先不」「属于后续工单」——这类句子写的时候都是真的，
所以它们**从来不会被判定为错**。它不是一个被写错的断言，是一个**过期的**断言，
而文本没有保质期这个概念：过期之后它不报错，只是安静地误导下一个读它的人，
而那个人回头去看，看到的仍然是一句读起来完全正常的话。

**写这类句子的时候，同时写下「什么事发生了它就该被删」。** 条件是可检查的，句子不是。

2026-08-21 扫了一遍仓库，四条里三条已经过期，各是一种不同的坏法：

**列举式的欠条，兑现一项就假一分。**
`session.go` 写着「日志、证书清单、探活回执在后续工单落地」——后两样就在它上面
几行处理掉了。句子读起来始终是完整的，没有任何一刻它看上去只对了三分之一。

**部分兑现的欠条比完全没兑现的危险。**
ADR-0004 写着「真要回答『流量真的通了吗』需要探活端点，那属于后续工单」。
探活端点做了——而它回的是隧道 RTT 和 Admin 可达性，**没有任何一个字段说流量通了**。
端点在那儿、名字叫探活，一个不细看的人会以为它兑现了。
完全没兑现的欠条一眼看得出还没做。

**挂在 issue 编号上的欠条，会随那张单子一起消失。**
`config.go` 写着「属于 #20 的系统设置」，#20 关了，那件事没做。
它不是被遗忘的，是被**归档**的——归档比遗忘更彻底，因为归档看起来像是处理过了。
欠条要么改挂一张开着的单子，要么就在原地把它做掉。

还有一种比过期更糟的：**承诺一件按现在的架构不该发生的事。**
`agent.go` 写着「证书续期在后续工单落地」，而证书随每次下发内联带上（ADR-0010），
根本不需要单独的续期指令。照那句话去实现，会做出一条与 ADR-0010 冲突的路径。
这种要的不是更新，是**删除**——proto 里那条消息已删并 reserved，
reserved 的注释正好是记录「为什么不做」的地方。

> 这条约定来自前端 agent 的观察。他那句话是：「『写的时候是真的』意味着它从来
> 没被判定为错。」


## 结论是代码，前提是世界

ADR 里写的「为什么」是一段推理。代码兑现的是那段推理的**结论**，测试保护的也是结论。
**推理的前提没人验**——而前提往往不是关于我们代码的断言，是关于外部世界的：
Caddy 会怎么答、数据库会被别处怎么写、官方包里有没有某个模块。

测试钉得住代码，钉不住世界。**能保护前提的测试，形状上必须真的去碰那个世界，
而且要跨越「别处」**——只测自己这一边，前提还是裸的。

2026-08-21 照这个标准查了一遍，三个前提，两个是裸的：

| ADR | 前提（关于世界） | 原先测的 | 现在 |
|---|---|---|---|
| 0014 | 心跳会冲掉同一列 | 分了两列（结论） | `store` 单测同时碰心跳写入与下线标记 |
| 0005 | 同一份字节喂同一个 Caddy 必然同样被拒 | 收到拒绝后不重推（结论，且用假回执） | 真 Caddy 连喂五次，断言拒绝与报错文本都一致 |
| 0003 | Agent 挂了 Caddy 会 fail-closed | —— | 已经有：真起 Caddy、真杀校验端点、断言 502 |
| 0001 / 0003 / policy | 官方 Caddy 没有 DNS / JWT / 限流模块 | 我们会拒绝（结论） | 跑 `caddy list-modules` 断言它们真的不在 |

最后那条的作用不是「保证它永远没有」，是**在它有了的那一天让人知道**：
它红了不代表代码错了，代表那几份 ADR 该重判。这类测试要在失败信息里把这句话说清楚，
否则下一个人会顺手把断言改掉让它变绿。

**检查器必须先证明自己不瞎。** 那条模块测试带一个反向自检：
如果 `list-modules` 哪天改了输出格式，三条「不存在」的断言会因为什么都没匹配到而全绿
——一个什么也没检查的检查器。前端 agent 撞见过同一件事的另一面：
他第一轮扫欠条用了后端的词汇（「属于 #N」「后续工单」），11 处命中全是误报，
因为他根本不写 issue 编号。**一次什么也没找到的扫描，要先证明它不瞎。**

> 「结论是代码，前提是世界」这个说法来自前端 agent。


## 否定断言天然会因为装置失效而变绿

「X 不在里面」和「我根本没打开那个盒子」产生同样的结果——而后者是**绿的**，
比红的更难被发现。肯定断言不吃这一套：装置坏了它直接炸。

所以**每一条否定断言都要自带一句自检**，证明装置是活的。不能靠旁边那条肯定断言
兜底：那种兜底是偶然的，否定断言自己读起来完全独立，谁把邻居删了或改窄了，
都不会觉得跟这里有关系。

2026-08-21 查了一遍，四条否定断言，全都对——但只有一条写明了自己为什么对：

| 断言 | 装置失效时 | 现在 |
|---|---|---|
| 官方 Caddy 没有那三个模块 | `list-modules` 换格式 → 全绿 | 断言输出里必须有 `reverse_proxy` |
| 路由表里没有多余端点 | `Routes()` 返回空 → 全绿 | 断言条数不少于契约端点数 |
| 回源 CA 连不上隧道 | （**不是这一族**，见下） | 断言失败原因是证书被拒 |
| 密钥 / 凭证不被回显 | 响应体为空 → 全绿 | 已有：同一份响应里的肯定断言 |

前两条各用探针验过（把 `list-modules` 换成 `version`、把路由表换成空 engine），
第三条用一个 `connection refused` 顶替真错误验过。

> 这个命名来自前端 agent。他那边整份前提检查脚本几乎全是这个形状
> （「密钥不被回显」「Token 不被回显」），所以自检对他不是锦上添花，
> 而是那些断言**能不能算数**的前置条件。


## 断言被「对象消失」满足

第三种坏法。不是装置没打开，也不是断言比意图宽——是断言**被「对象不再存在」
满足了**，而不是被「对象正确」满足。

前端 agent 撞见的原版是 Playwright：`expect(x.filter(...)).toHaveCount(0)`
在那一行整个消失之后成立，而匹配器**会重试到超时**，所以它安静地等到了
问题不再适用的那一刻。讽刺的是那个自动重试正是平时用来消除 flake 的东西。

后端这边同一个形状出现在 e2e 的 `isOnline`：它原先写着
`_ = json.Unmarshal(...)`，于是 `/nodes` 请求失败、响应结构变了、`Data` 是 null
——任何一种情况下 `Items` 都是空，函数返回 false，而 `stayOffline`
（「下线之后节点连不回来」）会一路绿地说「很好，它确实没连回来」。

现在它在拿不到数据时直接炸。探针验过：把 URL 改成一个不存在的路径，那条测试立刻红。

三种坏法的共同点：**「绿」这个信号被别的东西冒领了**——
没打开盒子 / 问了个太宽的问题 / 等到问题不再适用。

而 `waitOnline` 三种都不吃：它要求某件事**为真**，装置坏了它会超时报错。
**肯定断言天然带自检**，这是第三次印证。

## 断言比意图宽

跟上一条容易混，但它们是两个坏法：

- **装置失效** —— 断言在装置坏掉时变绿。装置好的时候它是对的。
- **断言比意图宽** —— 断言**在装置好的时候也是绿的**，它只是没在证你以为它在证的事。

`TestUpstreamCACannotAuthenticateToTunnel` 原先只断言 `err != nil`。那是
「有点什么不对」，而它想证的是「证书被拒」——端口分配失败、握手超时、
`keypair` 出错全都算数。这条测试从来没坏过，也从来没证过它的名字说的那件事。

**每次写一个宽断言（`err != nil`、`!= nil`、`> 0`、`toBeTruthy`），
先问一句「它为什么可能为真」。** 如果答案不止一个，而你只关心其中一个，
那就把那一个写出来。

> 前端 agent 指出这两条被我混成了一族。他的说法更准：
> 「不是装置失效，是断言比意图宽。」

## 测试名是唯一不会被执行的部分

断言会被跑、会红、会被改坏验证。**名字不会。** 它是测试文件里唯一一处
纯粹的声明，而声明没有执行就没有证伪。

前端 agent 撞见过一条名字与内容说反的测试（名字说「未绑定域名的规则不说那句话」，
内容拿一条**绑着域名**的规则断言它说了那句话，绿的）。他的根因分析值得照抄：

> 夹具表达不了那个状态，于是**名字写的是我想验的，内容写的是我能验的，
> 而没有任何东西比对这两者。**

同一族的还有「名字承诺得比断言多」：`TestSameBadConfigIsRejectedConsistently`
只覆盖 schema 类拒绝，环境类的已知有反例——那个边界写进了注释，
否则名字会替断言许下一个它兑现不了的承诺。

目前只有一条笨办法：**写完回头读一遍名字，问它跟断言是不是同一件事。**


## 改坏要从名字推，不从实现推

读着实现想「哪儿改一下会让断言失效」，只能验断言写对没有。
**从名字推**是另一件事：先构造一个让**名字说的那句话**为假的情形，再看测试红不红。
而**构造不出来本身就是答案**——它说明名字讲的事这个测试根本够不着。

2026-08-21 照这个过了一轮测试名，抓到一条，那条又牵出一个真 bug：

`TestDrainedNodeIsRefusedUntilRejoined` 名字说「被拒绝」，不限路径，
而它只测了 mTLS 重连。`identify` 里另一条 Token 路径的拒绝写了代码、
写了注释说明为什么该拒，一行测试都没有。补上之后**红在没预料的那一半**：
拒绝是通的，而 `rejoin` 之后那张下线前签好的 Token 已经废了——
`ConsumeEnrollToken` 查验与消耗一体，而它后面还有三步会失败，
其中两步是主控自己的内部错误。

**从实现推想不到这条**：读那个 `if` 只会问「改掉会不会红」，
而问题是「名字讲的事，测试够不着」。

> 这个办法来自前端 agent。他用它当场抓到三条，其中一条是
> 「测试断言的是我自己夹具里写的值，而名字说的是关于后端的事实」——
> **名字里藏着的前提，比代码里藏着的更难发现，因为代码至少会被执行。**

## 能钉住的理由是有限的一类

「一个正确的决定配了一个错的理由」比「决定错了」难发现：决定是对的，
所以没有任何东西会红。错的决定会撞墙，**错的理由只会在下一次有人照着它推论时才出事**。

`caddy list-modules` 那条测试之所以够得着理由，是因为那个理由恰好是一句
**可执行的事实断言**（「官方包里没有这个模块」）。而 #24 里我写错的那个理由
（「用 IP 的话换机器要重签」）是一句**推论**——由几个事实推出来，而推论不可执行。

所以：**写 ADR 的理由时先问一句「这是事实还是推论」。是事实的就顺手钉一条测试。**
推论只能靠有人回头重读，那没有办法，但至少可以少一类。


## 红了不等于验过了

改坏之后看到红色，只证明「有东西拦住了」，不证明「我想验的那条拦住了」。
红有三种打偏的方式，每一种都长得像验过了：

1. **新断言没被触发，旧断言先炸** —— 探针触发得太早。
   删路由那条探针放在 `UnbindDomain` 之前，红的是 `unbound_rules` 为空，
   而不是新加的「规则 wl 应当还在」。挪到摘完绑定之后才落在点上。
2. **改坏根本没生效，而结论碰巧正确** —— `perl -0pi -e` / `str.replace`
   静默不匹配。前端 agent 栽过一次：他据此认为「这条断言拦不住」，
   差点去改一条本来没问题的断言。他的复盘比「奖励了疏忽」准：
   **它把一次没有信息量的运行，变成了一次看起来有信息量的运行。**
   空结果会让人再看一眼，碰巧正确的结论会让人停下来。
3. **改坏生效了、语义确实坏了，而那条测试的观测点恰好看不见它** ——
   改动落在一个输出不变的分支上。前端撞见的：`if (drainedAt)` 换成
   `if (offline)` 之后，「已下线且离线」的机器仍然走进同一个分支、
   输出碰巧一样。**三种里这一种最像验过了。**

还有第四种，观测是**绿**的：**一条测试都没跑。** 改坏造成编译错误的话整个包
不编译，`go test` 输出里没有任何 Test 事件——而那跟「测试拦不住」是同一个观测，
结论却完全相反：一个是探针坏了，一个是测试坏了。
（`-run` 匹配不到名字、测试被 skip，同样表现为空。）

所以探针要回答**四问**：**改动落进文件了吗 / 目标测试真的跑了吗 /
它红了吗 / 红的是不是我想验的那一条**。第二问是正面自检——先证明那条测试
出现在这次运行里，后面两问才有意义。第四问看的是失败信息里的具体那句话，不是计数。

`scripts/probes.py` 把这一轮的改坏固化成 11 条，每条带上「它保护的是哪个不变量」。
跑法 `python3 scripts/probes.py [名字片段]`。

**脚本自己也要先证明不瞎**，三条都验过：改坏无害时报「没红」、
期望片段对不上时报「红在别处」、还原失败时点名污染的文件并 `exit 2`。

最后那条是前端强调的，理由值得原样留着：**一个会留下损伤的探针比没有探针更糟**
——它不只是自己不可信，它让后面所有测试的结论也变得不可信，
因为那些测试跑的不是真正的源码。

## 观测点分不开两个世界

比装置失效那三种更难防：**装置是好的、断言也不宽**，是那个观测点本身
分不开两个不同的世界。

`TestDeleteRouteUnbindsRules` 只断言「`/rules` 的响应里不含那个域名」——
而「摘掉绑定」和「规则整个没了」产生同一个观测。前三种坏法可以靠加自检、
收窄断言、换一次性读取解决；这一种只能靠**先问一句「还有什么别的世界
会产生这个观测」**。

它的对偶是上一节的第三种：**同一个世界在两个观测点下，一个变了一个没变**。
一个是观测点太粗，一个是观测点没对准。


## 手工维护的清单，防不住「忘了维护清单」

`contractEndpoints` 是一张手工表，存在的理由是「一个人的记忆不该是这件事的保障」。
2026-08-21 发现它漏了 `GET /nodes/:id/logs`——那个端点在契约里格式完整、
从来没注册过，而两条端点测试照旧全绿。

**一份用来防止人忘记的清单，自己被忘了。**

从契约自动生成更彻底，但这份文档里端点的写法不统一（有的是 `###` 标题，
有的在正文里，还有的是错误码表里的例子），全自动会把例子当端点、把变体当遗漏。
所以是**宽松扫描 + 具名豁免**：契约全文里形如 `` `METHOD /path` `` 的片段
都必须在某张清单里，豁免要写清为什么。

> 没有理由的豁免列表会变成垃圾桶，而垃圾桶里迟早会躺着一个真的遗漏。

同一次还发现：**「未实现的端点不注册也不给桩」这条原则只写在契约里**。
写在文档里的原则不会红，而一个悄悄加上的桩会被前端读成「还没有数据」。
现在标了「（未实现）」的端点被一条测试盯着——它必须**确实没有注册**。

## 换一个方向找空白

连续几轮打磨测试方法之后，值得停下来问一句产品面还有没有真的空白。
前端 agent 提出的排法是「**判断密度 vs 可测落点**」——判断多、而没有落点能验的地方。

后端这边有一个机械可查的入口：**写了但没人读的东西**。

```
DB 列  —— 建表/ALTER 里有，而任何 SELECT 都没出现过
proto  —— 字段定义了，而 Go 里既没有 Get 也没被直接读写
契约   —— 端点写了，而路由表里没有
```

2026-08-21 跑了一遍，三类各抓到一个真的（`traffic_samples` 整张表、
`LogBatch`、`GET /nodes/:id/logs`），加一个误报（`deploys.target_count`
被后来的迁移 DROP 了，扫描没处理 DROP COLUMN）。

**误报要当场说清，不然下次没人信这个扫描。**


## 元层的东西不受它自己保护

前端 agent 把这一族说清楚了，两个例子都是我这边的：

- `contractEndpoints` 是一份**用来防止人忘记**的清单，而它自己被忘了
  （漏了 `GET /nodes/:id/logs`）。
- 我把 `session.go` 那条过期注释改成一句自信的假话，而**改它的动机正是清理**。

第二条他归纳得比我准：**清理动作本身会给被清理的区域盖一个「已检查」的戳。**
下一个读到那句话的人不会去查那个端点——不是因为那句话可信，
是因为它**看起来是刚更新过的**。新鲜度被当成了正确性的代理。

`scripts/probes.py` 是同一族：它检查产品代码，而没有任何东西检查它。
我在写它的时候栽过一次（加第四问时，临时改动因为一个 `TypeError`
根本没落进文件，而我看到「11/11 通过」就往下走了）。

处置是 `python3 scripts/probes.py --self-test`：用刻意坏掉的 Probe 跑一遍，
断言脚本会给出正确的判词（没红 / 红在别处 / 改坏没匹配到 / 一条测试都没跑 /
还原不干净）。**手工跑一遍自检然后忘掉，跟固化探针之前的状态一模一样。**

**这一层封顶是合理的**，理由不是「没办法了」：产品代码的失败模式无穷，
而这个脚本只有四问、每问只有一种失败方式，可以枚举完。
验过——拆掉第二问或第四问，自检各红一条。

## 丢弃错误是安全的，当且仅当后果会被后续检查捕获

`_ = json.Unmarshal(...)` 这个动作长得跟真正的疏忽一模一样。它安全与否
取决于一个**隐式**的关系：解析失败留下的零值，会不会被下一步的判断兜住。

`dnsctl/cloudflare.go` 那处是安全的——解析失败时 `env.Success` 保持 `false`，
紧接着的 `!env.Success` 就会进错误分支并原样带出响应体。
但读的人得自己往下看一行才能推出来，所以那个理由现在写在注释里。

前端撞见的对偶：`.catch(() => {})` 吞掉 404，面板显示「暂无日志」——
**一句让人放心，一句让人去查**，而那四个字长得完全像一个正常的空态。
他反复截图看到它，一次都没怀疑过。


## 用完就丢的检查，只在写它的那一刻生效过一次

前端 agent 那句话，我这边有三个实例：`probes.py` 的三个自检（手工跑）、
「写了但没人读」那两类扫描（手工跑）、「带保质期的句子」那次词表扫描。

前两个已经固化：`scripts/probes.py --self-test`、`scripts/unread.py`。
第三个不适合——判断一句话有没有过期需要读它，机器给不出答案。

固化的时候有两个选择要做：

**误报要修，不要豁免。** `deploys.target_count` 是「写了没人读」扫描的第一个
误报——它被后来的迁移 `DROP COLUMN` 了，而扫描只看 CREATE/ADD。
加豁免会把「扫描不准」记成「这条不用管」，那是两件不同的事，
而记错之后没人会再回来分辨。

**盲区要说清，跟误报一样。** `unread.py` 的判据是「这个名字在源码里出现过吗」，
所以 `at` / `id` / `msg` / `lines` 这类短名会假阴性。不说的话，
「0 项是新的」会被读成「确实没有新问题」，而实际是「我这个筛子有洞」。

> 说清误报是在保护**真阳性**（不然第一次误报之后整个扫描会被忽略），
> 说清盲区是在保护**真阴性**（不然一次空结果会被当成一次证明）。
> 两句都不是道歉。

## 自检的第二种用处：给「没问题」提供证据

前端的 `--self-test` 第一次跑就抓到他脚本自己的 bug：vitest 默认 reporter
在**全绿**时不打印每条测试名，于是他的第二问（目标测试跑了吗）在全绿时永远
拿不到名字——而全绿正是第三问该开火的场合。判词会完全指错方向。

同一条自检在后端这边通过了，那不是「没抓到东西」——**它是 Go 的 `-json`
在 pass 时确实带测试名的证据**。手工验一次也能得到这个结论，
但那个结论会随着下一次 Go 版本升级过期，而自检不会。


## 我在自己的工具上犯了正在讨论的那个错

2026-08-21，跟前端 agent 来回讨论了好几轮「只看 N failed 不够，要看红在哪一条」
之后，我用一行内联 python 统计 `go test ./... -json`——**它只打印计数**。

某次跑出「通过=199 失败=1」，而我在同一个命令块里紧接着提交了。
那个 1 是什么，至今不知道：后来六轮都没能复现，现场没留下。

**现场没留下，那次运行就等于没跑过。**

两条教训，第二条更值钱：

1. 看到红就停，哪怕它是偶发的——尤其因为偶发的那次是唯一能抓住它的机会。
2. **说得出一个形状，跟在自己工具里认得出它，是两回事。**
   我给产品代码写了四问探针，给自己的统计留了一行只输出计数的 python。
   （前端说过同一句话的另一半：他给我报「没有表现成我没找到」，
   而他自己那条 `.catch(() => {})` 又活了好几轮。）

`scripts/gotest.py` 现在永远打印失败的包、测试名与完整输出，
编译错误那种非 JSON 行也单独列出——否则「0 失败」会是一句
关于一次根本没发生的运行的陈述。


## 打偏是探针的默认结果，对上才是例外

前端 agent 的归纳，来自第三次撞上同一个形状（我一次、他两次，最后一次
发生在一个**专门用来防这类问题的脚本**上）：

> 你构造一个你以为会触发 X 的情形，而系统在到达 X 之前先在别处停下了。

他验「exit 0 但一条都没跑」时，把 spec 路径指到不存在的目录——
而那让 vitest **exit 非 0**，走的是另一条分支。他验到的是「真失败会被打出来」，
那条早就验过了。

这句话改的是心态：不是「小心别打偏」，而是**默认就是打偏，所以每次都要单独确认
落点**。确认的方式是看失败信息里的具体那句话，不是看红不红。

配套的一条：**自检的靶子要挑「已知被覆盖」的测试。** 否则你验的是
「那块没有覆盖」，而不是「脚本认不认得出打偏」。我和他挑对靶子都是运气
（我挑「跑得快、不用 Caddy」的那条，他挑「最新写的」那个文件），
两边的理由现在都写进注释了。

## 自检把一句会过期的话变成一句不会过期的话

前端对「自检的第二种用处」的回话，比我原来的说法更进一层：

> 一次手工验证的产物是一个**事实**，一条自检的产物是一个**会跟着变的事实**。
> 前者写进注释就开始腐烂——那正是我们花了好几轮在清的那些
> 「写的时候都是真的」的句子。

所以自检不是给脚本加保险，是**把一句会过期的话变成一句不会过期的话**。

具体到「Go 的 `-json` 在 pass 时带测试名」：写进注释，它会在某次 Go 升级后
静静变假；写成一条自检，它会在那一天变红。


## 两个观测互相矛盾时，别挑一个信

第九格，前端 agent 归纳的，比前八格更基础：**前八格都是一个观测被误读，
这一格是两个观测不一致而我们做了选择。**

我查「编译错误在 stdout 还是 stderr」时跑了两个观测，结论相反。
我用了后一个，据此写了一段解析 stderr 的代码——跑出来 stderr 长度是 0。
正确答案在第一个观测里。

**选哪一个都可能对，但「做出选择」这个动作本身就是错的**：
矛盾说明至少有一个观测手段是坏的，而那件事比原来要查的问题更重要。

## 一个正则扫出来的名字，不带它属于哪个概念

前端 agent 为核对节点日志的 `level` 取值扫了 `level: '(\w+)'`，
报出一个大写的 `INFO`，就把它改成了小写——**而那是日志策略的 `level`
（契约 §6.3 规定大写），不是节点日志的**。

两个同名字段，取值规范相反，在契约里相隔几百行。现在两处互相指向对方了。

他自己的复盘值得留着：**打偏加上「顺手就改了」，比单纯打偏贵一档。**
前几轮的打偏只是报错了结论，这次改了文件，而 `typecheck` 照样绿——
枚举值是字符串字面量，改小写只会让界面显示「未设置」，
而那一屏不一定有人会去看。


## 理由要压在有变更流程的东西上

前端 agent 那句失效的注释（「traffic_samples 从来没被写过，这个 null 是永久的」）
让这一族有了名字。他给的可操作形式是**改写法**：把「因为你那边现在是 X」
写成「这依赖后端当前的 X」，让句子的语法自带保质期。

那个有用，但还有一层更硬的：**换掉理由本身**。

2026-08-21 扫了一遍后端注释里提到前端的地方，两处压在前端当前实现上：

| 原来的理由 | 换成 |
|---|---|
| `target_count` 保留是因为**前端已经在用它** | 因为**契约 §7 列了它** |
| 返回两份全文，因为 **diff 由前端用自己的 LCS 算** | 因为 **diff 在表示层算（ADR-0007）** |

两者说的是同一件事，但**前者会在对方改实现时静默失效，后者跟着契约/ADR
一起改——而那件事有流程**。

判据：写下一个理由时问一句「**它依赖的那个东西，改的时候会不会有人通知我**」。
契约会（改它等于改接口）、ADR 会（要写 supersedes）、对方的内部实现不会。

不是所有理由都能这样换。换不掉的那些，就照前端说的把保质期写进语法里。


## 观测能力变了，约束跟着变才是对的

前端 agent 在 `conns_delta_reason` 接上之后改了一组测试，他自己先说清了
那看起来像放松：

> 早先分不清是哪一种时，约束是「一律不承诺它会好起来」。现在分得清了，
> 约束落在「只对会自己好的那一种承诺」。**原来那条「一律不承诺」现在会挡住
> 一句真话。**

**一个约束的正确性取决于当时能观测到什么。** 观测能力变了而约束不变，
是刻舟求剑——那条旧约束会开始拦真话，而它读起来仍然像一条谨慎的好规矩。

这跟「理由变成数据」是同一件事的两面：**理由变成数据之后，
基于「我们不知道」建立的约束就该退役。**

改这类约束时要在提交里写清「它为什么现在可以更松」，
否则下一个人看到的是一次没有理由的放松。


## 顺手做对的配套决定，最容易漏进契约

删路由与删规则都会连它的草稿一起清掉——留一份指向已删资源的草稿，会让
「有几处未下发改动」算上一个再也下发不出去的东西。

这条行为从第一天就是这样，而**直到 2026-08-21 才写进契约**。
前端那边已经在依赖它，还为它单独写了一条前提检查。

**一个对方在依赖、而契约没写的行为，说明契约还不是完整的接缝。**

它为什么会漏：这类决定是主线功能的**配套**，实现的时候顺手就做对了，
而正因为不是主线，写契约的那一刻不会想到它们。

可操作的一条：**写完一个端点，问一句「它除了主线动作之外还改了什么」**
——清草稿、摘绑定、关解析、写事件，每一样都是别人可能依赖的行为。

## 防线设对层，看的是它保留了多少区分

前端 agent 给「一道为 A 设的防线兜住了 B」补了边界，这个补充比原话重要：

> 它也可能是**抽象层太高**——一道兜住太多东西的防线，会让每一种它兜住的
> 问题都显示成同一个样子。

他的例子是 `ErrorBoundary`：它救了整页白屏，但「后端给了 null」和
「我写错了一个 `.map`」在它眼里是同一件事，**它给出的信息量是一条**，
不管底下是哪一种。

所以判据不是「兜住了多少」，是「**兜住之后还分得出是哪一种吗**」。
`render` 的 `Issue` 带 `res_key` + `field` + `reason`，三类错误进去还是三类；
一个只回「这一页崩了」的防线，进去多少种出来都是一种。

## 检查的粒度要匹配被检查对象的结构

前端按**行**扫「用后端行为解释设计」的注释，141 处命中几乎全是误报——
因为理由写在多行块里，而契约引用在同一块的别的行上。按块重扫才是 18 处。

同一族的还有两个：`Requires=caddy.service` 那次假阳性（单行的检查看不见
多行的说明），以及他那个只排除注释起始行的 awk。

**前者是「单行看不见多行结构」，后者是「单行看不见同一块里的其他行」
——同一件事的两个方向。**


## 注释属于另一个函数

比「注释过期」更隐蔽的一种：**过期的注释描述的是曾经为真的行为，
而这一种从写下的那一刻起就是错的——它属于别的函数。**

2026-08-21 在 `PeekEnrollToken` 上撞到：那个注释块的头三行是
`ConsumeEnrollToken` 的，写着「原子地把 Token 标记为已用」——
**而那正是 Peek 明确不做的事，拆开这两个函数的全部意义就在那个区别上。**

成因很具体：拆函数的时候我把新说明加在了旧说明**后面**，没删掉旧的。
一个从上往下读的人，第一句话读到的就是反的。

前端 agent 在他的 `commit()` 上撞到同一族的另一个方向：注释承诺
「清掉草稿**并把版本推进**」，而函数体里没有一行动 version——那是靠调用点
紧跟着的 `fetchAll()` 拿回来的。**他的注释和代码「两条都成立」，
靠的是旁边一句它没提的话。**

顺手扫了一遍「注释首行的函数名与实际函数名对不上」，非测试文件里三处（都修了），
测试文件里七处**全是误报**——中文注释不以函数名开头，而首词恰好是
`Lark` / `Webhook` / `Caddy` 这类英文标识符。

**没有固化这个扫描**：误报率太高，而要压掉误报得写一堆限定条件，
那时它就成了一个只有作者看得懂的检查。做过一次、说清结论，比留下一个
会被忽略的检查好。


## 对外的陈述没人能替你核对

前端 agent 发出一条消息之后更正：里面有两句用了完成时（「我去把那句话补进了
注释」「我把那个口子补上了」），而**当时都还没做**。发完就去做了，两件现在
都真的在。

他的成因分析很准：**在写「我该怎么处置这件事」的时候，脑子里已经把处置想完了，
落到文字上就成了完成时。想清楚了和做完了之间那一步，恰好是最容易被自己跳过的。**

而这一类比注释里的同类更糟，理由是他说的：

> 注释还能被下一个读到它的人质疑，一句发出去的话不会——你没法查我，你只能信我。

两个 agent 隔着消息协作时，**对方报告的每一件事都是不可验证的**。仓库能查，
消息不能。

后端这边的工作流（执行 → 看输出 → 再报告）让这个错不容易犯，但**不是不会**：
2026-08-21 那次「通过=199 失败=1」，我在同一个命令块里跑完测试紧接着提交，
报告时没提那个失败——**同一个根源：把「我打算做的」当成「已经做的」**，
只不过我这次跳过的是「看一眼结果」而不是「动手」。

可操作的一条：**报告之前，把要说的每一件事回头对着仓库点一遍。**
这次点了四条（脚本在不在、豁免口子写没写、README 在不在、两处首句改没改），
成本是一个命令。

## 两类过期的注释，只有一类有机械手段

前端在补完那条测试注释之后发现：**那条注释的首句本身已经过期**——
写的是「后端在从没同步过时给的是零值时间」，而后端早就改成给 `null` 了。

而 `check:comments` 抓不到它：**它不含改正词，它是内容过期不是顺序错。**

两类分清了：

| | 例子 | 有机械手段吗 |
|---|---|---|
| **顺序错**（复盘占了首句） | 「这里原先写着…」 | 有：`scripts/comments.py` |
| **内容过期**（首句本身不再为真） | 「后端给的是零值时间」 | **没有** |

第二类包括我那个 `PeekEnrollToken`（首句属于另一个函数）。
目前只能靠**改动到那一带时重读**——而那正是最不可靠的办法，
因为改动的人往往只看他要改的那几行。


## 锚有三种，第三种一直在用而没说出口

「理由要压在有变更流程的东西上」那条判据，前端 agent 把它固化成了检查
（他扫「陈述后端行为的理由有没有挂在契约/ADR 上」）。我照着扫这边的
「陈述 Caddy / PostgreSQL 行为的理由」——**各自的「对方」不同**。

扫出来才发现判据本身少了一项：

| 锚 | 改了会怎样 |
|---|---|
| 契约 | 等于改接口，对方会知道 |
| ADR | 要写 supersedes |
| **测试** | **会红，而且它是自动的** |

第三种最强，而它此前**不可检**：一条「由某条测试守着」的理由，
除非注释里点了那条测试的名字，否则跟没有锚一样。

所以处置不是放宽判据，是**把注释改成点名那条测试**——
`ANCHOR` 认 `Test\w+`，「有没有锚」于是变成一个可查的信号。
六处扫描结果：一处真该挂 ADR-0003（挂了），四处的锚其实是测试（点名了），
一处是我的正则不认 `adr/0011-...` 这种文件路径写法（修了正则）。

## 粒度这个毛病换了三层尺度

前端连撞三次，每次比上一次小一层：

1. 单行看不见**多行结构**（扫 markdown 星号的 awk）
2. 单行看不见**同一块里的别的行**（扫欠条）
3. 整块看不见**句子边界**（扫理由的出处——一个讲纯前端取舍的块，
   因为顺带提了一句后端就被误报）

**每一次都是检查的粒度和被检查对象的结构不匹配，只是尺度换了一层。**

他自己的观察更值钱：**「注意粒度」这条提醒没起作用，起作用的是每次撞上
之后再降一层。** 所以这条写在这里的作用不是提醒，是给下一次撞上的人一个
现成的下一层——`comments.py` 的 `check_anchors` 直接从句子级开始，
省掉了前两次。


## 链接是单向的：守的一方知道，被守的一方不知道

前端 agent 先看见这个不对称：他的 `check-premises.mjs` **每条都标了「依赖处」
指向代码**，而**代码那一侧一句都没说自己被守着**。改那三行的人不知道
有一条前提检查在去问真主控。

后端完全一样：`scripts/probes.py` 里每条都写着它守着哪个不变量、改哪个文件，
而那七个被守的产品代码文件里**一句都没提探针**。改 `TouchHeartbeat` 那条 SQL
的人，此前完全不知道有一条探针盯着它——而那条 SQL 正是 ADR-0014 的核心论据。

补了七处反向链接。而**反向链接自己也会过期**：探针删了或改名，而代码里那句
「有一条盯着」还在——**那是最坏的一种假话，它让人以为有保护**。
所以 `comments.py` 查它。

**反方向不查**（一条探针没有反向链接只是少个指路牌，不是假话）。
前端那句是对的：两个方向的失效后果不同，不该用同一条规则。

## 「多处改动写在一个脚本里，一处失败全盘不生效」——今天第三次

三次都是同一个模式：一段 python 里连着改好几处，中间一处的 `old` 字符串
对不上，`SystemExit` / `AssertionError` 一抛，**后面的改动连同已经改好的
那部分一起没有写入**（因为 `write` 在最后）。

- 第一次：加探针第四问时，看到「11/11 通过」差点走过去
- 第二次：改四处注释的锚，被重扫结果（4 处仍命中）撞见
- 第三次：改 `check_backlinks` 的正则，被误报没消失撞见

**三次都是下一步的验证撞见的，没有一次是我自己发现的。**

处置有两条，第二条更根本：

1. 多处改动分开做，每步 `grep` 确认落地。
2. **每次改完立刻跑那个会告诉你结果的东西。** 前一条靠自觉，
   后一条靠机制——而这一整轮反复证明「靠下一步撞见」比「靠这一步小心」管用。

## 又一次 `git checkout` 冲掉未提交的改动

清理探针时跑了 `git checkout -- scripts/comments.py`，
把**刚写好但还没提交的 `check_backlinks` 整个冲掉了**。

前端栽过同一格（他冲掉的是 `link.ts` 里未提交的改动），我此前栽的是反方向
（对未跟踪文件跑 checkout，什么也没发生）。**同一个近似，第三次。**

正确的问法始终是「撤销我刚才那处改动」，而 `git checkout` 答的是
「回到 HEAD」。**探针脚本自己用的是快照比对（`path.read_text() != orig`），
手工清理时反而用了 git** —— 工具里做对的事，手上没做对。

**第四次（reqbody_test.go）。** 探完装置自检，跑 `git checkout internal/api/reqbody_test.go`
清理——那是一个**刚写完、还没提交**的新文件，checkout 对它什么也没做，
探针改动原地留着。而 `git status --short` 就在同一条命令里，
它把那个文件列成 `??`（未跟踪），**答案当时就在屏幕上**，我没读。

到这里可以收得更紧一句，因为四次的形状是同一个：
**恢复手段必须和修改手段对称。** 用 python 改的，用备份文件恢复；
用 git 管的，才用 git 恢复。跨过去就是在拿一个近似当精确用——
而这个近似的失败方式是**静默的**：它不报错，它什么也不做。

这次没造成后果，靠的不是小心，是那条自检：路由表拿到 < 20 个写端点就 `Fatalf`。
**探针留在原地的那份代码，正好会触发它自己探的那条断言。**


## 两句单独看都对，只有并排才看得出对不上账

前端 agent 的 seed 里出现过：`node-de-01` 在节点页显示「已下线（人为）」，
在 DNS 页显示「已暂停（abiu）」。他那是夹具从 `dns_enabled` + `status`
推 `dns_reason`，没看 `drained_at`。

**后端有一条真实路径能产生同一个状态**：已下线的机器点「暂停解析」，
`dns_reason` 被改写成 `manual`，而 `drained_at` 还在。

他那是夹具**缺**得不对，我这是产品代码**能造出**这个矛盾——后者更糟。

而两者难发现的原因是同一个：**每一句单独看都是对的**，
只有把两页并排才看得出账对不上。他是看截图发现的，而截图不是每次都看。

处置：两个方向都拒。而这不是「把约束改严了」——
**原来那条约束（关的方向不挡）有一个当时没看见的代价**。
改这类约束时要在提交里写清是哪一种：

| | 该怎么写 |
|---|---|
| 观测能力变了，旧约束开始拦真话 | 「它为什么**现在**可以更松」 |
| 发现了旧约束的一个代价 | 「原来那条漏了什么」 |

两者在 diff 里长得一样（一条断言反过来了），而理由完全不同。

前端 agent 照着写了一次，报回一个我没想到的后果：
**「原来那条漏了什么」这句话逼你说清旧理由至今成立。**

> 如果含糊写成「改严了」，读的人会以为旧理由错了，
> 然后下次遇到类似取舍时不敢用那个理由——而它是对的。

**一次含糊的修正会连带废掉一条好理由。** 而那条理由的死法是最安静的一种：
没有人删掉它，只是从此没有人敢用它。

## 「探针连启动都没启动」——又一格

前端验接入被拒时，事件流里什么都没有，**差一步就报「事件没写出来」**。
去看 agent 日志才发现它**根本没敲到门**：2020 端口被真 Agent 占着，
启动就退了。

比「探针打偏」更靠前一层：**打偏的探针至少运行了，这个连运行都没有**，
而失败的表现是「什么都没发生」——**跟「后端没写事件」产生同一个观测**。

## 观测手段截断了它要看的东西——第三次

`gotest.py` 存在的全部理由是留下失败现场。而这次它「没打印失败详情」，
查下来是**我自己的 `| tail -8` 把它截掉了**——脚本先打印 FAIL 块，
最后打印计数，而 `tail` 只留了最后几行。

前两次：`grep` 滤掉了 caddy 日志（我一度以为改动没生效）、
`cmd | tail; echo $?` 拿到 `tail` 的退出码。

**三次都是我为了「少看点输出」而加的东西，挡住了我要看的那部分。**
排查失败时应当先看完整输出，截断留给已经知道自己在找什么的时候。


## 我的环境替那个检查作了保

前端 agent 想验「没部署前端」那条路径，拿掉 `EC_WEB_ROOT` 重启——**照样绿**。
因为默认值 `web/dist` 是相对路径，而他正好在仓库根目录起的主控。

**一个检查在他的环境里恒绿，而恒绿的原因跟它要验的东西无关。**
不是装置坏了（装置好好的），不是断言太宽（断言很准），
是**那台机器碰巧满足了它的前提**。

跟「同名字段替真正的那个作了保」是一对：那个是**另一个东西**替它作保，
这个是**工作目录**替它作保。两者都要靠一次刻意的破坏才看得出来
——而「它绿了，说明能用」会让人跳过那一步。

后端这边的处置不是加检查，是**让那个前提可见**：主控启动时把 `WebRoot`
解析成绝对路径并打进日志（在不在都说）。不设变量时日志会写
`/Users/…/web/dist`，一眼看得出它在用仓库里那份。

**一行日志换掉一类「我以为部署了」。**

## 每一步都对，而终点是全错的

前端对「收敛到零」的补充，我认为是这一整天最锋利的一句：

> 这个过程的每一步都是**合理的局部判断**：看到一条改了不红的测试，
> 删掉它是对的动作。而整条路径通向零。
> **没有任何一步是错的，而终点是全错的。**

我们这一天讨论的其余失效模式，至少有一步能被指出来说「这儿错了」。
这一个没有——所以它只能靠**在测试里写下那句话**来打断
（「验它需要同时改两层」）。

## 可机械化的永远是「有没有链接」，不是「链接指对了没有」

前端指出 `check:anchors` 只验了 `契约 §7.2` 这个字符串在不在，
**没验 §7.2 讲的是不是他说的那件事**。

后端这边同构：`unread.py` 答得出「这个配置项有人读」，答不出
「读它的地方做的是不是它该做的事」——`EC_MTLS` 确实被读了，
而读它的地方只是设了个 Cookie 标志。

**前者是形式，后者是语义。这一天固化的所有检查几乎全停在形式那一层。**
那已经比什么都没有好很多，边界说清即可：**形式层的检查拦得住「忘了」，
拦不住「想错了」。**

## 响亮不等于指对方向

`EC_MTLS=1` 此前的后果是**登录不上**——那是个响亮的失败，
而它指向的是「登录挂了」，人心里想的是「我开了 mTLS」。

前端那句：**响亮不等于指对方向。** 跟「判词指错方向跟不报一样费时间」
是同一件事，只是它发生在一个安全开关上。

拒绝启动之所以是对的处置，不只因为它响亮，
更因为那条错误信息**把方向掰回来了**（说清它没实现、此前那个副作用会造成什么）。


## 检查和提交不该在同一个 `&&` 链里

2026-08-23：我在一个命令块里跑了「改注释 → gofmt → 跑 comments → 全量测试 →
git commit」。那处 replace 因为 **gofmt 已经把注释里的制表符重排成两个空格**
而没匹配到，python 抛了 `AssertionError`，输出里 `comments=1` 明明白白
——**而 commit 照样跑了**。

那个提交带着一个红着的检查。

**今天第五次「一处失败而我继续走」。** 前四次都是下一步的验证撞见的，
这一次我甚至看到了那个 `1`。

所以这条不是「多加小心」：**把 commit 从那种命令块里拿出来**。
检查和提交在同一个 `&&` 链里，等于让「检查红了」和「提交成功」
可以同时发生——而 `&&` 只在**退出码非零**时断链，
一个把结果打印成 `comments=1` 的命令，退出码是 `echo` 的 0。

（直接原因也记一下：**gofmt 会重排注释里的缩进**。「改完 gofmt」之后
再按原文匹配就会落空——改注释要么先 gofmt 再匹配，要么用正则按内容找。）


## 契约本身对不对，两边的测试都发现不了

这一天的分工是这样的：

| | 验的是 |
|---|---|
| 后端的 `internal/e2e` | 后端按**契约**行事 |
| 前端的测试 | 前端与**它想象的后端**接得上 |
| **只有「拿真产物连真主控」** | **契约本身对不对** |

2026-08-23 一轮里契约错了两处（「`{}` 会清空」是反的、§11 的字段表缺一半），
外加一处缺口（`GET /deploys` 的列表项回 `targets` 而 §7.3 没写）——
**三处都是那个动作撞出来的，没有一处是任何一边的测试发现的**。

它为什么难固化：**需要两边的产物同时在场**，而各自的检查都只有一边。

前端 agent 钉住了其中一块：`check:shapes` 拿真主控当基准，比对他的 mock
的响应形状（键集合 + 类型，不比值）。他的话点出了它跟别的检查的区别：

> `check:premises` 问「后端是不是我以为的那样」，能发现「后端变了」；
> `check:shapes` 问「我造的替身从一开始像不像」——而那正是这一轮三个 bug 的根。

后端这边能钉的一块是**结构体与契约的字段集**：`GET /deploys` 的列表项
直接序列化 `store.Deploy`，于是给那个结构体加字段会**静默多出一个契约没写的键**
（`targets` 就是这么漏出去的）。`TestDeployListItemFieldsMatchContract`
把那张表写进测试，加字段就红。

**这一类的通式**：凡是「响应体 = 直接序列化某个内部结构体」的地方，
那个结构体和契约之间没有任何东西——加字段不会红，改 json tag 也不会。

### 后来把中间那一块也钉上了

前端从**类型**里导出 `web/request-shapes.json`（不是手写：`shape<T>()` 强制
清单与 `T` 的键完全一致，漏一个多一个都编译不过），后端 `reqbody_test.go` 断言
**前端会发的字段，后端的结构体真的收得下**。

方向是刻意单向的。后端收得下而前端不发的字段不是错，那是还没做的界面；
反过来才是错。

**第一次跑就红，两处，都是真的。** 而两处的根都是契约，不是任何一边写错：

- 契约把 `GET /alerts` 和 `PUT /alerts` **并成一个代码块、一份 JSON**，
  读起来就是「PUT 发 GET 那个形状」。前端照做，`at_all_on_crit` 被包在 `lark` 里，
  而后端的结构体里它在顶层——静默丢弃，`code: 0`，界面显示「已保存」。
- 契约写「`ops_bot_token_configured` 同理」，把它和 DNS 凭证并列。
  **「同理」是假的**：它只从环境变量读，API 改不了。前端照着做了个输入框，
  而那个端点是严格绑定的——用户一打字，整个设置保存就崩。

### 过的那一半掩护了没过的那一半

`PUT /alerts` 这个 bug 最值得记的不是它本身，是它**为什么活了这么久**。

前端在真主控上验过这个端点：改「仅严重」→ 保存 → `notify_level` 真的变成 `crit`。
那次验证是真的，结论也是真的。**而 `notify_level` 恰好两边都在顶层。**

一次请求里有四个字段，三个对一个错，验的时候只看了对的那个。
**局部成功不但没暴露局部失败，还给了它掩护**——「这个端点我验过」从此成立，
而它成立的范围比说出口的窄得多。

前端 agent 回头看自己那次验证，给了一句更准的说法：

> 我不是验漏了，是**验中了唯一一个能过的**。挑一个字段验一个端点，
> 等于赌它是有代表性的那个。

对应的做法不是「每个字段都验」（那不可扩展），是让**形状**成为被检查的对象，
而不是让每次验证去抽查字段。这正是 `request-shapes.json` 这一层的位置。

### 形状必然不同时，要让它明显不同

`PUT /alerts` 的字段集**必然**与 `GET` 不同：GET 里只有 `url_configured: true/false`，
凭证不回显，没有地方放 webhook 地址。既然必然不同，就只剩两种写法：

1. 形状明显不同（平的 vs 嵌套的）
2. 形状看着一样、里面的字段名不一样（`webhook.url` vs `webhook.url_configured`）

选 1。**看着一样而实际不一样的形状，比明显不一样的形状更容易骗到人**——
第 2 种会诱使人「把 GET 回来的东西改一改发回去」，而那正是出事的动作。

同一条也解释了为什么不去拉平「写端点回不回对象」的不一致：
`PUT /dns/weights` 回归一化后的权重是真信息（发 3:1 可能存成 75:25），
`PUT /alerts` / `PUT /settings` 的 `null` 是真没有新信息。
**拉平的代价是回一份没用的东西，而没用的东西会被人当成有用的**——
前端两次白屏正是把 `data` 当状态用。

## 一个只在成功时挂死的检查

前端的 `check:shapes` 漏了 `process.exit(0)`：MSW 的拦截器挂住了事件循环，
而失败分支有 `exit(1)`，**所以前几次都正常结束——第一次全绿的时候它就再也不返回了**。

一个只在**成功**时挂死的检查步骤，会让流水线停在「看起来还在跑」上。
而它跟「一直红」的区别在于：红会被立刻处理，挂住只会让人等下去。


## 修好一个装置，会顺手让另一个装置失效，而失效的样子是绿的

2026-08-23 这一轮里这个形状出现了四次，两边各两次，值得单独立一格。

- 我的：`bindStrict` 写好之后**只挂在一个端点上**，而它解决的问题
  （写错的 key 得到 `code 0`）在每个写端点上都成立。`PUT /alerts` 就从那个缺口漏过去。
- 我的：探完装置自检，用 `git checkout` 清理一个**未跟踪**的新文件——什么也没发生，
  探针改动原地留着（见上面那一格，第四次）。
- 前端的：`check:shapes` 的 `PUT /alerts` 用例是「GET 一份现值再原样写回」。
  mock 改严之后 mock 回 1001、真主控回 0，而**两边的 `data` 都是 `null`，
  形状完全一致，所以它是绿的**——一个为验证而加的用例变成了什么也不验。
- 前端的：`check:shapes` 的用例表当时只列了出事的那一个端点，
  于是同形状的 `PUT /alerts` 白屏不会自己浮出来。

四次的共同点不是「忘了」，是**失效的表现形式与正常一模一样**。
所以对应的做法不是更仔细，是让装置的**覆盖面**本身成为被断言的对象：

- `TestEveryWriteRouteHasARequestBodySpec`：每个写路由都得在表里有一条。
- `TestEveryWriteEndpointRejectsUnknownFields`：清单从那张表来，
  新加端点忘了用严格绑定就会红。
- 前端那边：`check-requests` 扫源码里每个 `http.post/put/del`，路径没登记就红。

**「有没有漏掉一个」比「这一个对不对」更需要机械手段**，
因为漏掉的那个不会来找你。

### 顺带一条：类型标注只在字面量逐字段写出来时才管事

前端上一轮刚宣布「请求体有类型了，不再是 `Record<string, unknown>`」，
而告警页那行**带着 `AlertsPutBody` 的类型标注**，照样把 GET 的形状发了出去：

```ts
const body: AlertsPutBody = { ...form.value }   // 编译通过
```

展开一个变量不触发多余属性检查（excess property check 只对对象字面量生效）。
**一个看起来已经被类型管住的地方，实际上什么也没管住**——
又一次「装置在，而没接上」。

Go 这边没有对称的坑（`encoding/json` 本来就不看多余字段，
所以我们用的是 `DisallowUnknownFields` 这个显式开关），
但那句话是通的：**声明了约束不等于约束生效，要问的始终是「它什么时候真的会红」**。

### 登记表是上界，上界放宽了不会红

前端在 `request-shapes.json` 里登记了 `ops_bot_token`，
而**界面上根本没有那个输入框**——一句登记表里的假话。

他那边的 `check-requests` 只比端点、不比字段，所以「登记了但从不发」不会红。
方向上它 fails closed（吵而不是漏），比反过来好，
但那句假话是靠**后端这条断言**炸出来的。

这就是这套装置的真实分工：他那边保证「发出去的都登记了」，
我这边保证「登记的都收得下」——**而「登记的都真的会发」目前只有我这条能发现**。


## 破坏手段必须和断言对称

这是「恢复手段必须和修改手段对称」的上一格，前端 agent 撞出来的：

他要探 `check:shapes` 的 `code` 比对有没有用，选的破坏是把 mock 的 `ALLOWED`
集合改成 `['__nope__']`。跑完——**绿的**。差一点当成「探针证明它没问题」。

实际是：那条用例发的是空 body，`Object.keys({})` 是空的，
所以 `ALLOWED` 改成什么都不会触发拒绝。**他选的破坏对那条用例产生了完全相同的输出。**

> 我要验的是「code 不同会不会被发现」，就得让 code 真的不同，
> 而不是改一个恰好不参与这条路径的开关。

换成无条件 `return fail(1001)` 之后当场红了。

跟「恢复手段」那一格是同一件事的两半：**两次都是拿一个近似当精确用，
而两次那个近似的失败方式都是「什么也不做」。**

这也正是四问里第四问（「红在该红的地方吗」）之前那一问的实质：
**探针要断言的东西，和探针破坏的东西，必须是同一条因果链上的。**

## 一个带着理由的豁免，比没有豁免更难被怀疑

`TestEveryWriteEndpointRejectsUnknownFields` 里我给 `POST /auth/login` 写了：

```go
continue // 登录本身不带会话，单独由 TestUnknownFieldIsRejectedNotIgnored 一族覆盖
```

**那句话是假的**：那条测试验的是 `PUT /settings`，跟登录没关系。
于是登录的严格绑定**一条测试都没有**，而在清单里它看起来是被数过的。

真正的原因只是「它不需要发 Cookie」——那是**参数不同**，不是**不该测**。
改成 `send := auth; if 登录 { send = nil }`，两行，覆盖就回来了。
探针验过：把 `auth.go` 退回 `ShouldBindJSON`，它现在会红，
而且红出来的话是「得到的是"用户名或密码错误"」——
**一个拼错的字段会告诉你密码不对**，这正好又是那条顺序原则的例子。

一条空豁免会被人问「为什么」，一条**带理由的**豁免不会——
理由本身就是「已经想过了」的信号。所以：

**豁免的理由要能被机械核对，或者干脆别写理由，写「TODO 没覆盖」。**
`docs/api-contract.md` 里的 `contractMentionExemptions` 之所以还算安全，
是因为每一条豁免的对象都在同一个文件里、跑一次就能对上；
而我这条豁免指向的是**另一个测试的内容**，那是没人会去核对的方向。

前端 agent 那边的做法值得抄：`check:shapes` 现在按 `request-shapes.json` 对账，
每个写端点**要么在用例表里，要么在 `NOT_COMPARED` 里写明为什么不比**，
两样都没有就红。新加的端点默认落进「必须当场决定」，而不是默认消失。
2 个真比了，20 个写明理由，而多数理由是**做不到**（`POST /alerts/test`
要真往 Lark 群里发一张卡片），不是「没排上」。

**「没覆盖」和「覆盖了没问题」在输出里长得一模一样**——
这是这一整天反复出现的那个形状，覆盖账是它目前唯一的机械解。

## 「登记的都真的会发」：知道它靠巧合，就别当它被守着

三条断言的分工现在是：

| 谁 | 保证 |
|---|---|
| 前端 `check-requests` | 发出去的都登记了（扫源码里每个 `http.post/put/del`） |
| 后端 `reqbody_test` | 登记的都收得下（字段 ⊆ 结构体） |
| **没有人** | **登记的都真的会发** |

第三条今天被发现过一次（`ops_bot_token` 登记了而界面上根本没那个输入框），
但那是**巧合**：后端恰好也没有同名字段。要是后端有，两边全绿，那句假话就活下来了。

前端评估过补法：跑 e2e 时录下每个请求实际发出的键集，跟登记表比。没做，理由成立——
e2e 只覆盖工作台那几条路径，**没录到的会表现为「这个字段没被发过」，
而那跟「这个字段是假的」在输出里又是一样的**。同形状的坑，换了个位置而已。

写在这里是为了**让它不被误认为已经守住了**。
一个已知的空洞比一个自以为补上的空洞安全。


## 测试全都假设了产品到不了的那个状态

DNS 调度页上五条线路一个节点都没有，而库里有一台在线、`dns_enabled`、
没下线的节点。前端 agent 在真主控上撞到，列了三种可能，**没在界面上编解释**：

> 我没在界面上补解释，因为我不知道真的原因，而**编一个解释比不解释更糟**。

查下来是第三种，而且比「映射还没写」更糟——是个**闭环**：

- `dnssched.Build` 只遍历 `weights[line.Code]`，节点得先在 `dns_weights` 里有行才出现
- 写那张表的唯一入口是 `PUT /dns/weights`
- 界面只能改「已经在列表里的节点」

**新接入的节点永远进不了解析**，而这一页看起来完全正常：五条线路齐全，只是全空。
下线流程的第一步「摘解析」照样返回成功——摘的是一条从来不存在的记录。

这个洞能活到今天，原因值得单记：**`internal/dnssched` 里每一条测试都从一份
「节点已经在权重表里」的夹具开始**。8 条测试，覆盖了归一化、摘除、重新归一化、
全部离线、权重为 0、孤儿行、五条线路齐全——**没有一条从「一行权重都没有」开始**。

> 夹具替产品走完了产品自己走不完的那一步。

这跟「负向断言因夹具失效而变绿」是同一族，但更隐蔽：那一族里断言是空转的，
这一族里**断言全都真的跑了、也真的在验东西**——只是它们验的那个状态，
产品到不了。**测试通过率和产品可用性之间，夹具是那道可以骗过所有人的门。**

对应的问法，加进四问之后那一层：
**「这个夹具描述的状态，产品自己走得到吗？」**
走不到的话，缺的不是一条测试，是一条**路**。

### 两个都叫 line 的东西

`node.line`（`CN2 GIA`、`CMIN2`）是机房卖的**中转线路**，说的是这台机器怎么出网。
`line_code`（`ct/cu/cm/tw/ov`）是**访问者来自哪个运营商**。

一台 CN2 GIA 的机器同时服务电信、联通、移动的访问者是常态，两者之间没有函数关系。
而 `CONTEXT.md` 里**一个都没定义**——两个不同取值域共用一个词，
术语表里却是空的，这正是术语表该管而没管的那类事。

前端能问出「映射在哪一步做」这个问题，是因为他默认了有映射；
而默认有映射，是因为两个字段同名。**同名会制造一个不存在的承诺。**


## 「这张表的第一行是谁写的」——把闭环变成可逐张查的问题

DNS 那个闭环修完，问了一遍「还有没有第二个」。把它化成一个能逐张表查的问法：

> **这张表的第一行是谁写的？如果答案是「一个需要它已经有行的端点」，就是闭环。**

20 张表扫下来，`global_policies` 是**做对了的那个对照组**：`GetPolicy` 在
`pgx.ErrNoRows` 时回落到 `defaultPolicies`，所以 `GET /policies/tls` 在一行都没有时
仍然有定义的答案，界面据此能编辑、能存。

**救命的是「读的那一侧对空状态有定义的答案」**，而 `dns_weights` 恰恰没有。
这条比「记得初始化」更可靠：初始化会漏，而一个有定义的空状态是类型层面的事。

顺着这一遍还查出了第二个，形状不同但同族。

## 一份没有底子的草稿：报成功、删掉、什么也没建

`effective` 里三个循环都是「遍历 live 资源、有草稿就套上去」。
所以一份 res_key 在 live 里没有对应资源的草稿会被**静默跳过**，
而调用方随后 `DeleteDrafts(ctx, resKeys)` 无条件删。

实测的完整过程：

    写草稿 rule:brand-new  → GET /drafts 看得到，界面显示「待下发」
    预览                    → 完全不提它，validation.ok = true
    下发                    → 返回成功，有 cfg_version 和 deploy_id
    之后                    → 草稿没了，GET /rules 是空的

**成功的假象里最贵的一种：它同时是数据丢失。**

修法是接到已有的校验通道上，而不是造一个新的错误类型：预览 `validation.ok`
转假、下发用 `1002` 拒绝——**而下发被拒，DeleteDrafts 就跑不到，草稿因此活下来**。
「草稿活下来」是拒绝它的**主要理由**，不是副作用。

### 一条已有的测试靠着这个 bug 而通过

`TestDrainedNodeIsNotADeployTarget` 给一条**从没建过**的路由写草稿然后下发，
断言 targets 里没有已下线的节点。它一直是绿的——**因为孤儿草稿被静默吞掉了**，
下发照常成功，targets 断言照样成立。

修完 bug 它当场红。这跟 `dnssched` 那 8 条夹具是同一族的另一面：

| | |
|---|---|
| dnssched | 夹具描述的**状态**，产品自己到不了 |
| 这一条 | 夹具执行的**动作**，产品本不该允许 |

两者都表现为「测试全绿而产品坏了」，而且都不是「忘了写测试」——
**是测试写在了产品的语义之外，然后产品的缺陷把它接住了**。

所以那一问要问两遍：
**「这个夹具描述的状态，产品自己走得到吗？」**
**「这个夹具做的动作，产品本来允许吗？」**

第二问更难自觉，因为动作是自己写的、当时看着很自然。
唯一可靠的触发时机是**修了一个 bug 之后有别的测试红了**——
那一刻不要急着改测试让它变绿，先问那条测试原先为什么是绿的。


## 一个 flake 里藏着的生产 bug

跑全量时红了一条，再跑一次全绿。**没有当成噪音放过去**——现场文件还在，
里面那句是 `Post "http://caddy-admin/config/apps/http": EOF`。

这条路 Agent 在生产里也走，而且走的是**每一台全新机器首次下发必经的那一步**：
空 Caddyfile 的机器没有 `apps` 键，一定会先 `PUT /config/apps` 补一个空对象。

量了一遍（不是推理）：**Caddy 每一次写配置都会重启 admin 监听**。

    PUT  /config/apps       → admin endpoint started
    POST /config/apps/http  → admin endpoint started
    POST /config/apps/pki   → admin endpoint started
                            → stopped previous server（异步，滞后）

也就是每个写请求都会让**自己刚用过的那条连接作废**，而旧监听是异步关掉的。
窗口就在那儿：Go 从池里取出连接、正要写请求，那一头被关了。

### 复现不出来，恰恰印证了机制

顺序跑 30 次 0 失败。**把窗口人为拉宽到 80ms，还是 0 失败。**

那一刻的诱惑是「假设错了，算了」。但拉宽窗口反而更不容易出事这件事本身是个线索：
窗口宽的时候 Go 在取连接时就发现它死了，转而重新拨号。
真正会出事的是**恰好在取出之后、写入之前**被关掉——那需要机器负载够重，
也就是全量并行跑的那个场景。

**一个「越容易触发的条件下反而不出错」的现象，不是反证，是机制的指纹。**

### 修法不是重试

这个仓库里已经写过一次为什么：**重试会把「连不上」和「被拒绝」揉成一件事，
而 ADR-0005 的整套失败分类正建立在这两者的区分上。**

`DisableKeepAlives` 把窗口整个去掉：每次新拨一条，没有池子里的陈货可取。
而它在这里不是保守，是**对这个端点的准确描述**——每次写都作废，
连接池从来就没有可复用的东西。代价是每请求一次 unix connect。

### 白盒断言在这里是唯一诚实的选项

复现不出来的竞态，没有任何黑盒测试会在有人删掉那行时变红。
所以钉的是**那个决定本身**：断言 `DisableKeepAlives` 为真，理由写在旁边。

换成「跑一百次都没错」那种测试更糟：它平时全绿，回归之后大概率**还是全绿**。
**一个不会因为回归而变红的测试，提供的是保障的外观。**

### 顺带：替身要和被测对象在同一条路径上

`caddytest` 的 client 是同一套写法，也跟着改了。
flake 恰恰是在那个包的测试里现身的——**测试替身和被测对象在连接复用这件事上
必须一致，否则测试跑的是另一条路径**，而它跑得再多也不说明被测对象的事。

这和前端那条「跟着一起错的替身」是同一件事的另一面：
那边是替身继承了错的理解，这边是替身若不继承对的设置，就验不到真东西。


## 剥注释那一步，比判据本身更要紧

`humantext.py` 第一版的判据是对的，剥注释是错的，**两个方向都错**：

    line.split("//")[0]            → 字符串里的 http:// 被拦腰截断（假阴）
    只跳过「整行以 // 或 /* 开头」  → 块注释中间几行当代码扫（假阳）

第一种**前端 agent 提前警告过我**——他自己写 `check-requests` 时踩过，
在消息里专门写了一段：「从 `//` 一路剥到行尾会把字符串里的 `http://` 拦腰截断，
那时扫的就是另一种语言了」。我读过那段，然后照样写了 `split("//")[0]`。

> **警告和动手是两个时刻。** 读到一个坑不会在动手时自动浮上来——
> 它跟「修完一个 bug，同形状的另一个不会自己浮出来」是同一件事，
> 只是这次那个「同形状的另一个」在别人的仓库里。

第二种是他在自己那版里撞到的：第一次跑报 11 处，**8 处是他写在 `<!-- -->`
里的强调**。他的话点出了为什么这个方向更贵：

> 一个八成是误报的检查器，第二次就没人看了。

而它的失败方式不是「被删掉」，是**被忽略**——忽略和不存在没有区别，
只是还占着位置，让人以为这块被守住了。他差点给它写一句「先这样吧，
看的时候跳过那几条」，那正是「带着理由的豁免」的更差版本：**连理由都不用写，
人自己会在心里给它一个。**

改成走完整个文件的状态机（行注释 / 块注释 / 原始字符串 / rune / 双引号串各一态）
之后，四个方向都探过：块注释不误报、`//` 在串里能抓到、普通串照样抓、行号精确。

**顺带一个自己撞出来的事实**：字符串总数从 2839 掉到 2490。
旧版多出来的 349 个是它把注释文本当成代码扫出来的——
**那个数字一直印在成功输出里，而它一直是错的**。
装置自检看的是「有没有扫到东西」，看不出「扫到的是不是该扫的东西」。


## 互为兜底的两层，让单点破坏证明不了任何事——第二次

我在 `TestCannotEscapeWebRoot` 上栽过一次（存在性检查与实际伺服各自都足够，
单改一层另一层兜住，打偏了三次）。今天前端 agent 在他的打包校验上栽了同一格：

> 去掉 `chmodSync(stage, 0o755)`——**绿的**，而且输出照旧印着「顶层 `./` 也是」。
> 去掉 `normalize()`——也是绿的。两处都去掉才红。

**互为兜底本身是好设计**，它让系统更难坏。代价是**探针失去了分辨力**：
一次单点破坏产生的绿色，既可能是「测试是摆设」，也可能是「另一层顶上了」，
而这两件事在输出里一模一样。

所以规则要写成：

> **探一个有多层防护的不变量时，绿色不构成任何结论——
> 必须一直破坏到红，才知道自己在探什么。**

而危险在于第一次看到绿的时候人就想收工了。他的自述：

> 我第一次看到绿的时候，差点就收工了——那正是我自己那句「把没反应读成没毛病」，
> 而且是在我说完它之后一小时。

同一天里，「警告和动手是两个时刻」在两个方向上各应验一次：
我读过他的 `//` 剥注释警告然后照样踩了，他说完「把没反应读成没毛病」
一小时后照样差点收工。**这条不是关于粗心的，是关于「知道」和「用上」
之间那段距离的。**

## 两个 agent 共用一个工作树：`add` 和 `commit` 的宾语不是同一个东西

我跑 `git add -A internal cmd deploy` 之后 `git commit`，
把前端**已经暂存**的一个文件卷进了我的提交——作者是我，
提交信息跟那个文件毫无关系。

> **`git add <路径>` 限定的是这次加什么，而 `git commit` 提交的是整个暂存区。**
> 两个动词的宾语不是同一个东西，而它们看起来是。

他补的那一半同样要紧：他 `git add -A web/` 之后隔了好几步才 commit，
**那段时间暂存区就是个共享的雷**。

两边的处置一致：用 `git commit -o <路径>`，让「加」和「提」的范围强制一致。

他选择不 revert，理由成立：内容没动过，而 revert 再重提要制造两个额外的提交
**只为了让记录好看**。历史的可读性和记录的精确性在这里是冲突的，他选了前者
并在自己的提交里写清——那是对的取舍。


## 一个只报叶子的错误信息，会让所有人只看叶子——包括写它的人

灰度上「控制台静态文件不在」那件事，修完措辞之后**又错了一轮**。

第一版权限文案给的是 `ls -ld <EC_WEB_ROOT>`。现场照着做，看到
`drwxr-xr-x edge edge`——完全正常。于是又绕了一圈，我给的 `chown`/`chmod`
也只作用在那一层，跑完当然还是读不到。

直到 `namei -l` 才看出来坏的是 **`/opt` 本身**：

    drwx------ 501 staff  opt

0700，属主是 **UID 501 / 组 staff**——macOS 的账号，印在一台 Debian 上。
某个 macOS 打的归档以 root 解到了 `/opt`，把顶层 `./` 的属主和模式一起还原了。

**权限是逐层检查的，而那句报错里唯一出现的路径是 EC_WEB_ROOT。**
错误信息把注意力钉在叶子上，而坏的是路径上游一个跟这个项目毫无关系的目录。

> 报错要给的是**能扩大搜索范围的动作**，不是**能确认你当前假设的动作**。
> `ls -ld <那个目录>` 属于后者：它只能回答「这一层对不对」，
> 而人已经默认问题在这一层了。

现在给的是 `namei -l <完整路径>`：它不回答「那个文件怎么了」，
它回答「这条路每一层分别怎么了」。

同一格的另一面：`unread.py` 的盲区说明、`humantext.py` 的盲区说明，
都是在**主动扩大**读者的怀疑范围。而一句精确指向某一层的排查建议在缩小它。
**精确不总是好的——在还不知道问题在哪的时候，精确就是过早收敛。**

## 我把一个推断当成机制说了出去，而对方照着它改了提交信息

我给的诊断是「`--strip-components=1` 会把 `./` 的模式盖到目标目录本身」。
前端 agent 照着它改了包，**并把那句话写进了自己的提交信息**。

然后他去量了，量不出来：

    包里顶层:  drwx------  ./
    带 strip    解包后 dest 的模式: drwxr-xr-x
    不带 strip  解包后 dest 的模式: drwxr-xr-x

BSD tar、非 root，两种都不改目标目录。他自己更正了：

> 那是我照着你的诊断复述的，我没量过。

而 `namei` 出来之后证明**我那条在细节上确实错了**：`/opt/edge/web` 从来没有
变成 0700，被印上模式的是 `/opt`——也就是说那次解包根本没带 `-C`，
跟 `--strip-components` 无关。

我说那句时用的是陈述语气，没标「这是推断」。**一个带着确信语气的推断，
在别人那里会变成前提**——他改包是对的（顶层 755 无论如何都对），
但他的提交信息里从此有一句没人验过的因果。

对应的规矩：

> **跨 agent 传出去的因果链，要么带上是怎么量的，要么明说是推断。**
> 自己心里的置信度不会跟着消息一起传过去，而语气会。

这和「结论是代码，前提是世界」是同一条的下游：前提是从别人那里来的时候，
**它的可靠性取决于对方当时有没有说清那是量出来的还是想出来的**。


## 「我看过我的包了」——看的是顶层，没看属主

前端 agent 报 `/opt` 上那个 `drwx------ 501 staff` 是他的包带来的。
我当场去看自己的后端包，看到顶层是 `linux-amd64/`（具名目录，不是 `./`），
**就收手了**。

而每一行的属主那一列写着 `abiu/staff`。

以 root 用 GNU tar 解包时，恢复的是模式**和属主**。所以我的包同样会把
一台 macOS 的 UID 501 印到目标机器上——**同形状的另一个，又一次，
而且这次是别人刚把机制原原本本讲给我听之后**。

> 「我检查过了」这句话的范围，永远比它听起来窄。
> 它实际的意思是「我检查了我当时想到的那几件事」。

他补的那一条我没想到，而它是这件事真正的解：
`--uid 0 --gid 0` **还不够，必须带 --uname root --gname root**。
GNU tar 优先按**名字**解析属主，只归零数字的话，
目标机器上恰好有个叫 abiu 的用户，文件就落到他头上。

**归零是「做不到那件事」，解包后 chown 是「记得做」。**

## 不解析文本，就没有解析文本的那一整类 bug

前端在他那版校验里按位置数 `模式 链接数 属主 组 大小 日期 名字`，
而中文环境下 `tar tzvf` 的日期是 `8月 23 11:07`——**三段**。
于是「名字」从 `23` 开始，49 条全被判成路径错。

> **数错字段不会报错，它给出一个看起来很确定的错答案。**

这跟「报错只指叶子」是同族：**一个精确到具体位置的东西，
错了之后仍然精确，只是精确地指错。**

而 BSD tar 与 GNU tar 的列数还不一样（属主/组是一列还是两列）。
`scripts/packcheck.py` 用 Python 的 `tarfile` 直接读归档头字段——
没有文本、没有 locale、没有实现差异。**这一整类问题不是被处理了，是不存在。**

选「让问题不存在」而不是「把问题处理对」，判据是**它会不会随环境漂移**：
文本格式会（locale、tar 实现、版本），二进制头字段不会。

## 校验不过就不写校验和

`build.sh` 现在跑完 `packcheck.py` 才写 `SHA256SUMS`，不过就 `exit 1`。

前端的说法值得照抄：**一个没有校验和的包，是在说「别发它」。**
这把「这次记得检查」换成了「不检查就没有可发的东西」——
又一次把「记得做」换成「做不到」。

四条探针：拿掉属主归零、顶层是 `./`、目录 0700、空归档。都红在该红的地方。

**而探退出码时我自己栽了一次**：`bash scripts/build.sh | tail -5; echo $?`
拿到的是 `tail` 的退出码，不是脚本的。第一次量出来是 0，
差点读成「校验报了错但没拦住」。**观测手段截断了它要看的东西，第四次。**


## 「换个传输」和「换个身份模型」是两件事

灰度撞到 CDN 不转发 9000 之后，需求是「不要用 9000 了，改成走接口」。

字面照做的话是：隧道改成 WebSocket 挂在 `/api/v1/` 下 → Cloudflare 终止 TLS
→ **客户端证书到不了主控** → 节点身份得重做成应用层凭证 → ADR-0009 / 0013 重写
→ 而且 CDN 从此看得见隧道里的一切，**包括每个客户域名的私钥**（ADR-0010 内联下发）。

而实际只需要一句话：**`crypto/tls` 和 gRPC 都只要一个 `net.Conn`。**

把 WebSocket 包装成 `net.Conn`，原来那套 mTLS 握手在**它里面**跑。
proto 不动、tunnel 不动、agent 业务不动、`identify()` 不动、ADR 不动。
新增的是一个 conn 适配器和一个由 HTTP handler 供料的 listener。

> **需求说的是「走哪条路」，而字面实现把它读成了「换一套身份」。**
> 两者之所以会混，是因为在通常的做法里传输层顺便提供了身份
> （TLS 客户端证书）。一旦把这两件事拆开看，就只剩传输那一件要换。

代价是 TLS-in-TLS 两层加密。对一条心跳几秒一次的控制面连接可以忽略，
而换来的是中间那层看不见里面。**这不是洁癖**：隧道里传的是私钥。

## 装配漏了要响，不能静默 404 —— 我在自己的注释下面 30 行犯了它

新端点我写的是：

```go
if o.Tunnel != nil {
    v1.GET("/tunnel", ...)
}
```

而同一个函数里、下面 30 行就是 `/ws` 那段，注释写着：

> **无条件注册。** 条件注册意味着装配漏了 Hub 时这个端点会静默 404，
> 而 404 读起来是「没实现」而不是「配错了」——排查方向完全不同。

那段注释是我写的。**测试当场红了**（契约里有而路由表里没有），
但它红的原因是测试夹具没装隧道——如果测试恰好装了，这个洞会一直在。

这一天里「知道和用上是两回事」出现了四次，两次在我身上，两次在前端那边。
它跟粗心无关：**那段注释在文件里，不在我写 `if` 的那一刻的脑子里。**

## 契约里的路径写法不一致，扫描器会替你说出来

新小节的标题我写成 `### \`GET /api/v1/tunnel\``，而其余小节都用裸路径
（`### \`GET /alerts\``）。契约扫描器给路径补 `/api/v1` 前缀，于是它报：

    契约里提到这些端点，而两张清单都没有它们：
      GET /api/v1/api/v1/tunnel

**那个双前缀本身就是诊断**——它不只说「对不上」，还说清了对不上的方式。
一条把中间过程露出来的错误信息，比一条只给结论的省一轮排查。


## 一个手工补丁挡住了一次，挡不住第二次

`comments.py` 的索引检查只扫 `scripts/`，而 `edge-node_test.sh` 住在 `deploy/`
——当初的处置是**手工 add 一行**：

```python
real.add("edge-node_test.sh")  # 它住在 deploy/，但索引里该有它
```

今天 `deploy/` 下多了 `cf-realip.sh`，索引里提到了它，**而检查对它一无所知**。

> 手工补丁修的是「这一个例外」，而例外通常不是最后一个。
> 判据很简单：**如果这个补丁是因为「它在另一个目录」而加的，
> 那么下一个在那个目录里的东西会重复这个问题。**

改成扫两个目录之后，两个方向都探过（漏登记会红、指向不存在的会红）。

顺带又撞到今天那个主题：失效引用的报错原先写死了 `scripts/` 前缀，
于是一条 `deploy/` 下的失效引用会被报成 `scripts/` 下的——
**人会去那个目录找，找不到，然后怀疑是检查器坏了**。改成原样回显索引里的路径。

## 来源 IP：CDN 那一层比「记成 127.0.0.1」更难发现

审计记成 `127.0.0.1`（反代自己）是个显眼的错，看一眼就知道不对。
而挂在 CDN 后面时记下的是**CDN 边缘节点的公网 IP**：

> 它看起来像一个真实的公网地址，人不会怀疑它。

灰度上就是这样，是逐条检查响应头时顺带发现的——**没有任何东西会报错**。

处置里有两个决定值得记：

**一、反代只转一个值，不转一条链。**

`$proxy_add_x_forwarded_for` 追加，主控收到 `<访问者自己写的>, <真实来源>`，
得从右往左走，而走对的前提是可信代理名单一个不漏。
`X-Forwarded-For $remote_addr` 替换，主控只收到一个值，
链上根本没有访问者写的部分可解读。

**选让问题不存在，而不是把问题处理对。** 代价是丢掉上游链条——
而那条链本来就是攻击者可写的，留着只是噪音。

**二、IP 段不手抄，而且取回来的东西要校验。**

手抄会过期，而过期的表现是「某些访问者的 IP 又变回 CDN 的地址」，
没有任何东西会报错。`cf-realip.sh` 从 Cloudflare 公布的列表生成。

而这个脚本自己有一条承重的校验：**取回来的每一行都得像 CIDR，
而且总数不能少于 10 条**。取到一页 HTML 错误页照单写进去的话，
nginx 要么起不来（好），要么把一段谁都能落进去的范围当成可信（很坏）。
三条探针验过（HTML 错误页 / 只有两条 / 有一行不带前缀长度）。

**它的降级方向也是对的**：文件缺失时 real_ip 整段失效，来源 IP 退回 CDN 地址
——不准，但不可伪造。**一个安全机制失效时，要退到「更少信息」而不是「更多信任」。**


## 检查器自己崩了 —— 而这次报告是先打出来的

灰度上跑 `edge-node.sh verify`，六条全 ✓，然后：

    ./edge-node.sh: line 1: ss_out: unbound variable

成因是 `trap 'rm -f "$ss_out"' EXIT`。**单引号让 `$ss_out` 留到退出那一刻才
求值**，而它是 `local` 的，函数一返回就出了作用域，`set -u` 于是报错。

前端 agent 今天早些时候栽的是同一格的**更坏版本**：他的检查器崩在报告之前，
于是人看到一句 `ENOENT`，而真诊断躺在数组里没能说出口。他的话：

> 一个自己会崩的检查器，比一个报错不清的检查器更糟：后者至少在说话。

我这个报告先出来了，所以只丢了退出码——**而那不是小事**：
任何按 `verify` 结果判断的地方，都会把一台完全健康的节点当成失败。

### 判据：变量的寿命短于 trap 的寿命时，在设置那一刻就展开

    trap 'rm -f "$x"' EXIT     # 退出时才求值 —— x 必须那时还活着
    trap "rm -f '$x'" EXIT     # 设置时就展开 —— x 现在活着就够了

`cf-realip.sh` 里那个 `tmp` 是全局的，单引号其实也对。仍然改成同一种写法：
**同一种形式，就不需要每次去想作用域**，也不会在有人把那段代码挪进函数时重现。

### 一条在这台机器上永远不会红的断言

我给这个 bug 写了两条否定断言：`hasnt "unbound variable"` 和 `hasnt "line 1:"`。
探针放回旧代码时，**只有第一条红了**——macOS 的 bash 报的是
`bash: ss_out: unbound variable`，不带 `line 1:`。

删掉了第二条。**一条不会红的断言不是多一层保障，是伪装成覆盖的噪音**——
而它比没有断言更糟，因为清单上多一行会让人觉得这里被看得更严。

（这也是「探针要落在多跳那一侧」的另一种形态：探针不只告诉你断言有没有用，
还告诉你**哪一条**有用。两条一起绿看不出区别，一起红才看得出。）


## 一道防误报的措施，造出了一个永久的漏报

灰度上一台机器 31 分钟没心跳，控制台显示「在线」。前端 agent 查到根因、
给了完整证据链，而我的第一反应是先核对——**今天已经因为把没核对的机制
当事实说出去栽过三次**。核对之后一字不差。

`m.nodes` 只在**收到心跳时**才建条目。主控重启后 map 清空，
而一台已经失联的机器再也不会发心跳，就永远进不了这张 map——
tick 遍历不到它，`SetNodeDown` 一次也不会被调用。

**而制造这个洞的，正是 tick 上面那段注释：**

> 判定用「连续错过 N 个周期」而不是「距上次心跳超过 N×周期」：
> 后者在主控刚启动、还没收到任何心跳时会把全部节点判成离线，
> 而它们可能一直好好的。

那个顾虑是对的。但「数错过的次数」**只对已经在 map 里的节点数**——
不在 map 里的从来不被数，于是永远不会到达阈值。

> **一道防误报的措施，把误报换成了一个永久的漏报。**
> 而两者的可见度完全不对称：误报会吵，漏报只是安静地什么都不发生。

修法没有推翻那个顾虑：启动时把库里的节点装进 map，misses 从 0 开始，
一台真死的机器仍然要连续错过 Threshold 个周期才被标记——
**跟一台在主控运行期间死掉的机器走同一条路径、同样的延迟**。

### 连带后果比现象贵

`SetNodeDown` 同时做三件事：写库、**摘解析**、**发离线告警**。
所以这个 bug 的实际形态不是「徽标显示错了」，是

- 一台死机器还挂在解析里 —— 流量会往它上面打
- 没有任何人被通知

灰度上没造成实害，只因为 DNS 服务商还没配上。**「没出事」和「不会出事」
是两回事**，而前者常常被当成后者。

### 重启不能重复报警

装载时有一条是承重的：**库里已经是 down 的，要标成「已报过」**。
不标的话每次主控重启都会为同一台死机器再发一次告警、再摘一次解析。

**一个重启就重复报警的系统，会教会运维忽略那一类告警**——
跟 markDown 里「被人下线的节点不报离线」是同一条理由，同一份代码里已经写过一遍。

前端因此不知道手边有个比 `status` 更实时的信号，只能按契约认 `status`。

这跟今天早上 `GET /deploys` 的 `targets` 是同一族，而通式也已经写过：
**凡是「响应体 = 直接序列化某个结构体」的地方，那个结构体和契约之间
没有任何东西。**

`nodeResp` 是手写的，所以那条通式不直接适用——但缺口是同一个：
**加一个字段不需要经过任何门。**

补进契约时没有把它升格成第二个「在线」信号（那会让 ADR-0014 的两格模型
变成三格），而是写清了各自回答什么问题、以及**短暂不一致是正常的、
持续不一致是 bug**。


## 三条探针全是坏的，而救我的是 gotest.py 的自检

给「节点编辑/删除」写完测试之后探了三条，输出是：

    探针一：通过=0 失败=0
    探针二：通过=0 失败=0
    探针三：红了，但红在 SQL 报错上，不是断言上

前两条是**编译失败**——我的破坏留下了未使用的变量和 import。
如果 `gotest.py` 只打印「失败=0」，我会把它们读成「探针红了」或者更糟，
读成「没问题」。而它打的是**「一条测试都没跑 —— 名字打错了？包路径不对？
这不是『没问题』，是一次没有发生过的运行」**。

第三条更隐蔽：它确实红了，但红的原因是 pgx 不接受一次 Exec 里两条语句，
**跟我要验的东西毫无关系**。一条红了的探针一样可能什么都没证明。

改成编译得过、SQL 也对的破坏之后，三条各自红在该红的断言上。

> **探针本身要先跑起来，然后才谈它红在哪。**
> 「没跑起来」和「跑了但不红」在失败计数上是同一个数字。

这跟前端那条「把没反应读成没毛病」是同一格的更前一步：
他那次药没进去，我这次**针都没扎进去**。

## 「删记录」和「撤掉那台机器」是两件事，而只有一句话能说清

`DELETE /nodes/:id` 删的是主控这边的记录。**那台机器上的 Agent 和 Caddy 还在跑**
——它还在监听 80/443，还在用最后一次拿到的配置服务。

人点完删除会以为干净了。所以响应里必须带着那句「要真正撤掉在那台机器上执行
`edge-node.sh uninstall`」，而且界面要原样显示它。

**一个只做了一半的操作，必须自己说出另一半是什么。**
这跟今天早些时候那条「返回的 ok 要说的是解析真的变了，不是库里写成功了」
是同一条：**成功的范围，要跟成功的措辞一样宽。**

### 前提不是礼节性的确认

删除要求节点先下线，理由不是「危险操作二次确认」：

一台还连着的机器手里有隧道证书。删掉记录之后它会重连、会被 `identify()`
按证书认出来、然后在一张不存在的行上写心跳——`TouchHeartbeat` 是 UPDATE，
影响 0 行，**不报错**。结果是一台连着、在服务、而控制台上看不见的机器。

下线断隧道并拒绝重连（ADR-0014），所以它是这个操作**真正的前提**。
判据：**如果去掉这个检查会产生一个不一致的状态，那它是前提；
如果只是「后果严重」，那才是确认。** 两者在界面上的措辞应当不同。

### 跟着删的与留下的，是设计时就分开的两类

    dns_weights / cert_nodes / node_logs   外键级联 —— 关于这个节点此刻的**安排**
    deploy_results / events / audit_logs   没有外键 —— 已经发生的**事**

「那次下发推到了哪几台」「谁在什么时候下线了它」——
**删掉一台机器不该让过去发生过的事从记录里消失。**


## 探针只能碰自己写的东西 —— 我用队友正在编辑的文件当素材，把它冲掉了

探「只动 `web/` 时后端的包不该被标成 dirty」，我需要一个脏文件，
于是用了手边现成的那个：

```bash
echo "// probe" >> web/src/model.ts && bash scripts/build.sh
git checkout web/src/model.ts 2>/dev/null || python3 -c "...去掉那一行..."
```

那是前端 agent **正在编辑、尚未提交**的文件。`git checkout` 成功了，
所以 python 兜底没跑——而它成功的方式是把整个文件退回 HEAD。
unstaged 的改动不在 git 的对象库里，**恢复不了**。

两个错，第二个是新的：

**一、`git checkout` 冲掉未提交的改动，今天第五次。**
我为此写过规矩：**恢复手段必须和修改手段对称**——用 `>>` 加的，
就用去掉那一行来恢复。而我把正确做法写成了 **fallback**，
fallback 只在错误做法失败时才跑。

> **把正确做法放在 `||` 右边，等于把它放在永远不会执行的位置。**
> 那不是"有兜底"，那是"写了一份自己看着安心的东西"。

**二、探针的素材取自别人的工作区。**
以前没出现过，因为以前我只动自己的目录。补一条：

> **探针只能碰自己写的东西。** 需要一个脏文件就 `touch` 一个新的，
> 或者动自己目录里的。**手边现成 ≠ 可以拿来用**，
> 尤其在一个两个 agent 共用工作树的仓库里。

这跟早些时候那条「`git add <路径>` 限定的是这次加什么，
而 `git commit` 提交的是整个暂存区」是同一族：
**共用工作树的时候，每一个默认作用域都比它看起来的宽。**

## 一个用来消除歧义的东西，自己带着歧义

`master_version` 加进 `GET /overview`，理由是前端在灰度上分不清
「修得不对」和「根本没部署」。加完之后打包，产物叫
`edge-controller-af7e03b-dirty`。

那个 `-dirty` 来自前端在 `web/` 下的三个未提交文件——
**而后端二进制里根本没有 `web/` 的任何东西**。

> 一个说「这个构建含未提交改动」而实际不含的版本戳，**比没有版本戳更坏**：
> 它会让人去找一个不存在的差异。

判据：**版本戳的作用域必须和产物的作用域一致。**
`git describe --dirty` 看整个工作树，而产物只含其中一部分——
在单人仓库里这两者恰好重合，所以这个 bug 一直不显形。

**一个默认值在它诞生的环境里恰好是对的，换个环境就不是了**——
而它不会因此报错，只会开始说一句略微不真的话。
