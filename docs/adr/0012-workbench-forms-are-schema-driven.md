# 工作台表单由字段描述表驱动，不是三个手写表单组件

- 状态：已接受
- 日期：2026-08-21
- 相关：[ADR-0007](0007-workbench-preview-is-a-representation.md)（右栏是可读表示）

前端开发文档 §2 把工作台的表单列为三个组件：`RouteForm.vue` / `RuleForm.vue` /
`PolicyForm.vue`。不这么做：做一个字段渲染器加五种字段控件，每类资源提供一张**字段描述表**。

「三个」这个数字本身就不成立。路由 1 套字段，访问规则按 `type` 分 **3** 套
（IP 白名单 / 服务密钥 / JWT），全局策略 **2** 套（TLS / 日志限流）——实际是 6 套布局，
不是 3 套。高保真设计稿也正是这么实现的：`wbFieldsFor(key)` 返回字段描述数组，
markup 用一个循环渲染，五种控件（文本 / 多行 / 分段 / 开关 / 域名 chips）覆盖全部资源类型。

## Considered Options

- **三个手写表单组件**（文档字面方案）。模板可读、类型直接。但工作台每个字段都有三种统一
  行为——**改动着色**（值与基线不同则边框转 accent）、**错误着色**（非法 IP 让输入框转红并
  禁用下发）、**hint 随值切换**（`abort` 与 `403` 的提示文案不同）。手写就要写六遍，
  而这三种行为恰恰是「改配置怕推错」这条主线的可见部分，写六遍等于给它六个跑偏的机会。
- **控件组件化 + 六处手写布局**。着色逻辑不重复了，但布局仍要写六遍。

## Consequences

- 新增一种资源类型或一个字段，改的是描述表，不是组件树。
- schema 驱动的表单容易滑进 `value: any` 的泥潭。字段描述用可辨识联合
  （`{ kind: 'text' | 'area' | 'seg' | 'switch' | 'chips' }`）打类型，每张表用
  `satisfies FieldSpec<RouteDraft>[]` 绑到该资源的草稿类型上——否则这条 ADR 用类型安全
  换来的东西会被自己抵消掉。
- 单测的形状随之改变：测的是「描述表 + 一份草稿 → 期望的字段状态」这个纯函数，
  而不是挂载三个组件各点一遍。
