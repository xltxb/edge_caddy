# 控制台准入靠「只绑内网 + 会话 Cookie + 全写审计」，mTLS 是可关的开关

- 状态：已接受
- 日期：2026-08-21
- 相关：[ADR-0004](0004-no-master-side-caddy-validate.md)（主控不装 Caddy）

三份文档对「控制台自己怎么被保护」给了三个不同答案：PRD §7 说走 **mTLS**，
后端 §4 说 **HttpOnly Cookie 会话 + ops-bot 静态 Bearer**，后端 §8 说
**只监听内网 / 经 Caddy 反代加 IP 白名单**。

决定：master 自己监听，**不前置 Caddy**；准入是「只绑内网或回环」+ Cookie 会话 +
全部写操作与登录（含失败）留审计。远程访问走 SSH 隧道 / WireGuard，不由本系统解决。
mTLS 以 Go 原生 `tls.Config.ClientAuth` 实现为一个**配置开关，默认关**。

## 为什么不前置 Caddy

后端 §8 那句直接抵触 ADR-0004。ADR-0004 的好处是「主控上不存在 Caddy 版本」，
装一台来做反代就把这个性质吃掉一半——即使只用它反代不用它校验，机器上仍然多了一个
要跟版本、要打 CVE 的 Caddy，而排查时「主控上的 Caddy」和「节点上的 Caddy」会被混为一谈。
Go 的 `http.Server` 本来就能做 TLS 终止与客户端证书校验，不需要它。

## 为什么 mTLS 默认关

只有一个人用。浏览器客户端证书的运维成本（多设备分发、轮换、丢失后的自锁）全部落在
同一个人头上，而它防的是「已经进到内网的攻击者」——在当前威胁模型里，这个增量小于成本。
开关留着：哪天控制台要从内网挪出去，翻开关即可，不需要重做准入。

## 实现状态（2026-08-22 补）

**「mTLS 以 `tls.Config.ClientAuth` 实现为一个默认关的开关」这一半从来没有写。**

`EC_MTLS` 被读进了配置，而它唯一的效果是决定会话 Cookie 的 `Secure` 标志
——那与 mTLS 是两件事，而且在纯 HTTP 的主控上会让人**登录不上**
（浏览器不在 HTTP 连接上发送 `Secure` Cookie）。

也就是说：**翻开那个开关，mTLS 不会发生，而人会以为它发生了。**
这件事没有任何症状，直到有人真的去中间人。

处置：`EC_MTLS=1` 现在**拒绝启动**（`config.ValidateMTLS`），
错误信息说清它没实现、此前那个副作用会造成什么、现在该怎么办。
**把一个静默的假象换成一个响亮的失败**，与 `EC_ADVERTISE` 同一条处置。

> 这一条是前端 agent 提醒去查的。他给的区分很准：一个默认关的**功能**开关
> 关着时什么也不做；一个默认关的**安全**开关关着时，是一条安全路径不执行
> ——**前者的失效是「多了个不该在的东西」，后者的失效是「以为开着其实关着」**。

真要实现它，除了 `ClientAuth` 本身，还要一并做下面 Consequences 里那条
**回环逃生口**：开着 mTLS 又弄丢证书时，回环上的监听必须仍然可用。

## Consequences

- **需要一个回环逃生口**。开着 mTLS 又弄丢证书时，回环上的监听必须仍然可用，
  否则会把唯一的运维人员锁在系统外面。
- 「只绑内网」是**部署形态**而不是代码里的检查。代码只负责绑定地址可配，绑错地方
  （比如 `0.0.0.0`）不会有任何东西报警——部署脚本要显式校验这一点。
- ops-bot 继续用静态 Bearer Token（后端 §4）。开关翻开后它要改用客户端证书，
  届时这条要一并处理。
- 要改 PRD §7 与后端文档 §8。
