# 内部 PKI：两套独立 CA，主控持根，回源叶子 24 小时

系统里有两处 mTLS，用途完全不同：**回源**（边缘节点向源站证明身份，
见 [ADR-0008](0008-route-mtls-is-upstream-client-cert.md)）与**隧道**（Agent 向主控证明身份，
后端文档 §8）。两者各用一套独立 CA，均由主控持有根私钥，边缘节点上**不存在任何 CA 私钥**。

| | 回源 CA（edge-mtls） | 隧道 CA |
|---|---|---|
| 信任方 | 各源站 | 主控 |
| 叶子有效期 | 24 小时 | 长期（接入时下发） |
| 续期通道 | gRPC 隧道，自动 | 隧道，远早于到期 |
| 吊销方式 | 停止续期 | 主控侧移除该节点 |

## 为什么不共用一个 CA

- **换根的影响面不同**。换 edge-mtls 根要协调每一个源站的信任库；换隧道根只关系到主控自己。
  共用一个根意味着源站侧的一次轮换会同时把所有节点踢下控制面——而那正是你最需要控制面
  去下发新证书的时刻。这个循环依赖必须在设计阶段断开，事后断不了。
- **寿命策略被迫一致**。回源叶子要短（吊销靠过期），隧道证书要长（见下）；同一套 CA 硬凑
  会让其中一边取错值。

## 为什么回源叶子取 24 小时

内部 PKI 的 CRL / OCSP 基本没人真部署，写了也是摆设——一个不会被查询的吊销列表等于没有吊销。
把叶子做短，吊销就退化成「停止续期」这一个动作，不需要新机制，而隧道本来就在。

代价是节点与主控失联超过 24 小时后回源 mTLS 失效。这是可接受的：一台你整天联系不上的机器，
不该继续拿着凭据进你的源站。隧道恢复后自动续上，无需人工干预。

## 隧道证书为什么不能也做短

会死锁：隧道证书过期 → 连不上主控 → 拿不到新证书 → 永远连不上。所以隧道证书取长期，
并在远早于到期时通过隧道续期。万一仍然过期（节点停机数月），恢复路径是**重新走接入流程**——
一次性 Token + 安装脚本本来就存在，不必为此另造机制。

## 接入时的先有鸡先有蛋

首次连接时节点还没有隧道证书，因此不能用 mTLS 客户端认证。接入握手用
**服务端单向 TLS + 一次性 Token**，主控在这次交换中签发并下发隧道客户端证书；
此后该节点的所有连接都用 mTLS。Token 用后即失效。
