# 不在主控侧跑 caddy validate

后端文档 §6 要求下发前在主控本机跑 `caddy validate --config`，失败即整体拒绝、不触达节点。
不这么做：主控不安装 Caddy 二进制，改为渲染器自身的 Go 层校验（重复域名、空回源、
`body_max` 非法、访问规则缺必填字段等），再依赖节点侧本来就有的原子拒绝。

## Consequences

实测（Caddy 2.11.4，先跑一份可用配置，再 POST 各种坏配置）：

| 失败情形 | HTTP | 在跑的配置 |
|---|---|---|
| JSON 语法错误 | 500 | 存活 |
| 未知 handler | 500 | 存活 |
| 字段类型错（`max_size` 给字符串） | 500 | 存活 |
| 端口已被占用 | 500 | 存活 |

- **一份坏配置打不挂节点**：Caddy 每一次都保留了原配置。主控侧预校验想提供的安全保障，
  节点侧本来就有。省下预校验，代价只是「用户点了下发后看到 N 个节点失败」而不是
  「点下发时立刻报错」——是体验损失，不是安全损失。
- 主控不必安装 Caddy，也就没有「主控用一个版本校验、节点跑另一个版本」这个错位陷阱。
  该陷阱的两种表现都很难排查：主控放行而节点集体拒绝，或主控拦下一份节点其实能跑的配置。
- Go 层校验拦不住 Caddy schema 层面的错（比如我们把某个 handler 字段名写错）。这类错误
  会在首次下发时以「全部节点失败 + 同一条 Caddy 报错」的形式暴露，逐节点结果里看得到原文，
  且不会有节点受损。渲染器的单测应覆盖每种 handler 的产出形状。

## 复核（2026-08-21，Caddy 2.11.4 / macOS 15）

装上钉死版本的 Caddy 后重跑了上表。**四行里三行逐字复现，第四行不复现。**

| 失败情形 | 原表 | 实测 | 在跑的配置 |
|---|---|---|---|
| JSON 语法错误 | 500 | **500** ✓ | 存活 |
| 未知 handler | 500 | **500** ✓ | 存活 |
| 字段类型错（`max_size` 给字符串） | 500 | **500** ✓ | 存活 |
| 端口已被占用 | 500 | **200** ✗ | 存活 |

端口冲突那一行实际发生的事，比「返回码不对」更值得记：

```
POST 之前，18099 的监听者：Python
POST 返回：                http=200，响应体为空
POST 之后，18099 的监听者：Python + caddy   ← 两个都在
Caddy 的 config：          servers = [srv0, srv9]
打 18099：                 无响应（流量进了 Python）
Caddy 日志的 error/warn：  一条 error 都没有
```

**Caddy 报成功、配置里有那个 server、日志无错，而它收不到任何流量。**

这几乎肯定是 macOS 的 socket 语义（BSD 的 `SO_REUSEADDR` 允许对同一 addr:port
重复 bind），生产节点跑 Linux，行为很可能不同——**但这一点没有在 Linux 上验证过**，
不要把它当成已知。

### 这不动摇本 ADR，但改掉它的一条论据

本 ADR 的结论仍然成立，且理由更强了：`caddy validate` 是**静态**检查，
它本来就发现不了端口冲突——那要到真正 bind 的时候才知道。所以主控侧预校验
在这个情形下什么也提供不了。「一份坏配置打不挂节点」四行全部验证通过。

要改的是 [ADR-0005](0005-retry-only-transport-failures.md) 的措辞：那条说
「Caddy 对各种坏配置一律返回 500，因此无法按状态码分类」。**更准确的说法是：
返回码与失败与否根本不是一一对应的**——不仅坏配置都是 500，还存在返回 200
而实际没有生效的情形。按状态码分类因此更不可行，结论不变。

### 给 #18 的直接后果

**`PushResult{ok:true}` 的含义是「Caddy 接受了这份配置」，不是「流量正在被服务」。**
这个区别必须在代码与界面措辞里保持诚实，和「配置漂移只比对版本号」
（[ADR-0002](0002-drift-is-version-comparison.md)）是同一类问题：
一个听起来更强的承诺，兑现不了。

真要回答「流量真的通了吗」，需要一次实际的请求——探活端点是自然的位置，
但那属于后续工单，不在 #18。

> **2026-08-21 补：探活端点做了，而它并没有答这个问题。**
>
> `POST /nodes/:id/probe` 回的是隧道 RTT 与本机 Admin 的可达性——
> 「Agent 活着」「Caddy 活着」。**没有任何一个字段说流量通了。**
>
> 这条欠条因此仍然成立，只是它现在更容易被误读：端点在那儿，名字叫探活，
> 一个不细看的人会以为它已经兑现了上面那段话。
>
> **一个部分兑现的欠条比完全没兑现的危险**——后者一眼看得出还没做。

## 又一次兑现（2026-08-21）：回源 mTLS 的字段名写错了

本 ADR 说「Go 层校验拦不住 Caddy schema 层面的错（比如我们把某个 handler
字段名写错）」。#22 实现回源 mTLS 时正好发生了一次：

渲染器把客户端证书路径写成了 `transport` 上的 `tls_client_certificate_file`，
而正确位置是 `transport.tls` **对象里面**的 `client_certificate_file`。

```
json: unknown field "tls_client_certificate_file"
```

**渲染器的单测（golden 快照）照样通过**——它只能证明「我渲染出了我想渲染的
东西」。抓到它的是 `internal/caddytest` 那条真 Caddy 的集成测试。

这正是当初决定「不打 //go:build integration 标签、让它默认就跑」的理由：
一个默认不跑的测试等于没有测试，而这类错误的另一种暴露方式是生产首次下发时
「全部节点飘红」。
