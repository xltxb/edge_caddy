# 检查脚本

按**你此刻在做什么**排的，不是按脚本本身的分类——一份索引要匹配读它的人当时的
处境，而不是内容的归类（这条判据来自后端，它也是这么切 `scripts/README.md` 的）。

## 改完代码，提交之前

```bash
pnpm check          # 5 步：类型、单测、模板标记、复盘注释首句、e2e
pnpm check:fast     # 同上但跳过 e2e（约 30 秒 → 约 3 秒）
```

**它保证失败不会被压成一个数字。** 我这一整轮都在用 `vitest run | grep "Tests"`
只看那行计数，而我有前科：`5bb2dd9` 是红着提交的。所以这个脚本永远打印失败细节、
永远打印跑了多少条（「0 失败」在一条都没跑的时候同样成立，而两种处置相反），
并且**非零退出**——让 `&&` 链断在这里，而不是让 `git commit` 跑起来。

## 改完之后想知道「测试真的拦得住吗」

```bash
pnpm check:probes        # 13 条：故意改坏源码，看该红的那条红没红
pnpm check:probes:self   # 4 条：探针自己还认不认得出它该认出的失败
```

**不在 `pnpm check` 里，因为它真的会改源码再还原。** 跑它之前工作区最好是干净的
——它跑完会逐字节比对，确认还原干净了；但如果进程被杀在中间，损伤会留下。

每条探针回答四问，缺一不可：改动真落进文件了吗 / 目标测试真跑了吗 / 红了吗 /
**红的是不是我想验的那一条**。第四问是这个脚本存在的理由——「我加的那条拦住了」
和「旧的那条先炸了」在终端上都是一片红。

`:self` 是给这个脚本本身的：那四问此前是我手工验的，而手工验一遍然后忘掉等于没有。
它第一次跑就抓到了探针自己的一个 bug（vitest 默认 reporter 全绿时不打印测试名）。

## 改完之后想知道「我对后端的假设还成立吗」

```bash
pnpm check:premises      # 9 条，需要真主控在 localhost:8080
```

**单测里的 fetch 是我造的，e2e 里的后端是我写的 mock**——两者都能证明代码兑现了
我的假设，都证明不了假设本身成立。而假设失效时，代码是绿的。

每条都标出「依赖处」：哪一行代码压在这条前提上。它红了**不一定意味着前端有 bug**，
而是那处代码的理由已经失效，该重判理由而不是把断言改绿。

## DNS 凭据配上之后（还没轮到）

```bash
pnpm check:certs         # 5 条，需要真主控 + 已配的 DNS 服务商
```

**凭据没配时它以 exit 3 退出并说「这一遍还没轮到」** —— 那不是失败。

写成脚本而不是留一句「凭据到了我跑一遍」，是因为**那句话我说了很多轮而它一直
只存在于句子里**。一句发出去的话没有人能查，一个脚本可以被跑。

它验：证书两列真相对得上账（差额 = missing_nodes 条数）、ACME 签的走 dns-01
且不是内部 CA、手动续期受理、`dns_sync.ok` 转真且 at 是真实时刻、下线第一步
真摘解析且排空那步保留了 TTL 边界那句。跑完会把动过的节点复原。

那几条断言的**逻辑**在 `src/certs-assertions.test.ts` 里拿夹具跑着 —— 因为
**这个脚本写完那天，它的主体一条都没执行过**，而一个从没跑过的检查跟一句承诺
没有区别。

## 打包上线之前

```bash
pnpm check:dist          # 会先构建，再查产物里有没有不该有的东西
```

第一次打包时 `mockServiceWorker.js` 混进了包里 —— 注册那段有 `import.meta.env.DEV`
守着所以不会被启用，**但它仍然会被部署到主控上并且可以被直接访问**。
「不会被启用」和「不在那儿」是两件事，而只有后者不依赖那句守卫一直正确。

顺带钉住 index.html 的资源路径是**根绝对路径** —— 深层路由要靠伺服方做
SPA fallback（真起过静态服务器验：没有 fallback 时 `/nodes` 是 404）。

## 单独跑某一项

```bash
pnpm check:templates   # 模板里有没有会被字面渲染的 markdown 标记（我犯过两次）
pnpm check:comments    # 含复盘的注释块，首句是不是在讲被改掉的那件事
pnpm check:anchors     # 用后端行为讲的理由，挂没挂在会通知我的东西上
```

`check:anchors` 的判据：**它依赖的那个东西，改的时候会不会有人通知我。**
契约会（改它等于改接口），ADR 会（要写 supersedes）；对方的内部实现不会。
挂不上的不是不许写，是要把保质期写进句子里——「这依赖后端当前的 X」读起来
自带提醒，「后端会 X」读起来像一条恒真的道理。

这两条快且无副作用，所以也在 `pnpm check` 里。单独跑只是为了改的时候快速回看。

## 为什么不全合并成一条

触发时机不同：`check` 每次提交前都该跑；`check:premises` 只在主控起着、且我动了
跟后端有关的假设时有意义；`check:probes` 要真改坏源码再还原。

合成一条的代价不是时间，是**人会开始忽略其中几条的输出**——而那时它们跟不存在
没有区别。（这条也是后端的判断，我这边成立的理由一样。）

## 一个共同的形状

这几个脚本里的断言多数是**否定的**（「不该出现 X」「不该有 Y」），而否定断言
天然会在装置失效时变绿——「X 不在里面」和「我根本没打开那个盒子」产生同样的结果。

所以每一个都先有一道**正面自检**：`check-premises` 先证明登录成功、`check-templates`
先证明真的解析出了模板、`check-comments` 先证明真的找到了含复盘的块、`probe` 先证明
目标测试真的跑过。**自检不过就中止，不再往下报结论**——因为那时下面每一条「没问题」
都不作数。
